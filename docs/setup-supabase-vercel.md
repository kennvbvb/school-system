# คู่มือตั้งค่า Supabase + Vercel ทีละขั้น

> คู่มือนี้พาตั้งค่า **บนคลาวด์** ตั้งแต่ศูนย์จนเปิดเว็บใช้งานได้
> สำหรับการรันบนเครื่องตัวเอง ดู [`deployment.md`](deployment.md) หัวข้อ "ตั้งค่าสำหรับพัฒนาในเครื่อง"
>
> เวลาที่ใช้โดยประมาณ: 30–45 นาที สำหรับรอบแรก

## ก่อนเริ่ม — ทำไมต้องมี Supabase 2 โครงการ

แผนข้อ 17.1 กำหนดว่า **Preview ห้ามเชื่อมฐานข้อมูล Production** เพราะทุก Pull Request
จะสร้าง Preview deployment ที่เข้าถึงฐานข้อมูลนั้นได้ ถ้าใช้โครงการเดียวกัน
ข้อมูลจริงของโรงเรียนจะถูกอ่านและแก้ได้จากทุก PR ซึ่งผิดทั้งแผนและหลัก PDPA

| Environment ใน Vercel       | โครงการ Supabase           | ข้อมูลข้างใน          |
| --------------------------- | -------------------------- | --------------------- |
| Production                  | `school-procurement-prod`  | ข้อมูลจริงของโรงเรียน |
| Preview                     | `school-procurement-dev`   | ข้อมูลสมมติเท่านั้น   |
| Development (เครื่องตัวเอง) | Supabase local ผ่าน Docker | ข้อมูลสมมติ           |

**คู่มือนี้ให้ตั้ง `dev` ให้เสร็จก่อน** แล้วค่อยทำ `prod` ซ้ำขั้นตอนเดิมตอนใกล้ใช้งานจริง
เพราะถ้าพลาดตอนทดลอง จะได้ไม่กระทบข้อมูลจริง

## ขั้นที่ 1 — สร้างโครงการ Supabase

1. เข้า [supabase.com/dashboard](https://supabase.com/dashboard) แล้วกด **New project**
2. กรอกข้อมูล:

   | ช่อง              | ค่าที่แนะนำ                                                    |
   | ----------------- | -------------------------------------------------------------- |
   | Name              | `school-procurement-dev`                                       |
   | Database Password | กดสุ่ม แล้ว**เก็บไว้ในที่ปลอดภัย**                             |
   | Region            | `Southeast Asia (Singapore)` — ใกล้ไทยที่สุด ทำให้เว็บเร็วขึ้น |
   | Plan              | Free พอสำหรับ dev                                              |

3. รอสร้างเสร็จประมาณ 2 นาที

> **รหัสผ่านฐานข้อมูล** ใช้ตอนเชื่อมด้วย CLI และตอนกู้คืนข้อมูล
> ถ้าลืมต้อง reset ใหม่ อย่าเก็บไว้ในไฟล์ที่ commit ขึ้น GitHub

## ขั้นที่ 2 — สร้างตารางและ RLS

โครงการที่เพิ่งสร้างยังว่างเปล่า ต้องรัน migration ทั้ง 2 ไฟล์ตามลำดับ

เลือกวิธีใดวิธีหนึ่ง

### วิธี ก — SQL Editor (ง่ายกว่า ไม่ต้องติดตั้งอะไร)

1. เปิด Supabase Dashboard → **SQL Editor** → **New query**
2. คัดลอกเนื้อหาทั้งไฟล์ `supabase/migrations/20260903000100_core_identity.sql` มาวาง → กด **Run**
3. เปิด query ใหม่ คัดลอก `supabase/migrations/20260903000200_rls_policies.sql` มาวาง → กด **Run**

> **ต้องรันตามลำดับเลขหน้าไฟล์** ไฟล์ที่สองสร้าง policy บนตารางที่ไฟล์แรกสร้างไว้
> ถ้ารันสลับกันจะได้ error ว่าไม่พบตาราง

### วิธี ข — Supabase CLI (เหมาะเมื่อจะแก้ schema บ่อย)

```bash
npx supabase login
npx supabase link --project-ref <project-ref>
npx supabase db push
```

`<project-ref>` คือรหัสในหน้า Project Settings → General → Reference ID
(หรือดูจาก URL: `supabase.com/dashboard/project/<project-ref>`)

### ตรวจว่าสำเร็จ

Dashboard → **Table Editor** ต้องเห็น 8 ตาราง:

`departments` · `positions` · `profiles` · `permissions` · `roles` · `role_permissions` · `user_roles` · `audit_events`

## ขั้นที่ 3 — ใส่ข้อมูลตั้งต้น (สำคัญ ห้ามข้าม)

`supabase db push` **ไม่ได้รันไฟล์ seed ให้** ต้องรันเอง

seed แยกเป็น 2 ไฟล์ที่มีหน้าที่ต่างกันชัดเจน:

| ไฟล์                          | เนื้อหา                      |    dev     |      prod      |
| ----------------------------- | ---------------------------- | :--------: | :------------: |
| `supabase/seed-reference.sql` | สิทธิ์ บทบาท และการผูกสิทธิ์ | ✅ ต้องรัน | ✅ **ต้องรัน** |
| `supabase/seed-sample.sql`    | หน่วยงานและตำแหน่งตัวอย่าง   | ✅ รันได้  | ❌ **ห้ามรัน** |

> **`seed-reference.sql` ไม่ใช่ข้อมูลทดสอบ** — เป็นรายการสิทธิ์และบทบาทที่ผูกกับโค้ดใน
> `src/domain/auth/permissions.ts` โดยตรง ถ้าไม่รัน ระบบสิทธิ์จะไม่ทำงานเลย
> ผู้ใช้จะเข้าสู่ระบบได้แต่ไม่เห็นเมนูใดเลยสักอัน

**สำหรับ dev:** เปิด SQL Editor รัน `seed-reference.sql` ก่อน แล้วตามด้วย `seed-sample.sql`

**สำหรับ prod:** รันเฉพาะ `seed-reference.sql` แล้วบันทึกหน่วยงานและตำแหน่งจริง
ของโรงเรียนเองผ่านหน้าจัดการข้อมูลพื้นฐาน (Phase 2) หรือด้วย SQL ที่เขียนขึ้นเฉพาะ

ทั้งสองไฟล์รันซ้ำได้ปลอดภัย ทุกคำสั่งมี `on conflict` กำกับไว้

### ตรวจว่าสำเร็จ

```sql
select (select count(*) from public.permissions) as สิทธิ์,
       (select count(*) from public.roles) as บทบาท,
       (select count(*) from public.role_permissions) as การผูกสิทธิ์;
```

ต้องได้ **สิทธิ์ 25 · บทบาท 8** ถ้าได้ 0 แปลว่ายังไม่ได้รัน `seed-reference.sql`

## ขั้นที่ 4 — ปิดการสมัครสมาชิกบนคลาวด์ (สำคัญมาก)

> ⚠️ **จุดที่พลาดกันบ่อยที่สุด**
>
> ไฟล์ `supabase/config.toml` ที่ตั้ง `enable_signup = false` ไว้
> **มีผลเฉพาะ Supabase ที่รันบนเครื่องตัวเอง** ไม่มีผลกับโครงการบนคลาวด์
>
> ต้องไปปิดใน Dashboard เองอีกครั้ง มิฉะนั้นใครก็ตามที่รู้ URL กับ anon key
> จะสมัครบัญชีเข้ามาเองได้ ซึ่งขัด **FR-AUTH-002** โดยตรง

1. Dashboard → **Authentication** → **Sign In / Providers**
2. ที่ **Email** ให้ปิด **Allow new users to sign up**
3. เปิด **Confirm email** ไว้ตามเดิม

ถึงจะมีชั้นป้องกันในแอปอยู่แล้ว (บัญชีที่ไม่มีแถวใน `profiles` ใช้งานระบบไม่ได้)
แต่การปิดตั้งแต่ชั้น Supabase ทำให้ไม่มีบัญชีขยะเกิดขึ้นเลยตั้งแต่แรก

## ขั้นที่ 5 — คัดลอกกุญแจ

Dashboard → **Project Settings** → **API**

| ต้องการ                         | ชื่อในหน้า Supabase | หน้าตา                         |
| ------------------------------- | ------------------- | ------------------------------ |
| `NEXT_PUBLIC_SUPABASE_URL`      | Project URL         | `https://abcdefgh.supabase.co` |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | anon / public       | สตริงยาวขึ้นต้นด้วย `eyJ...`   |

> **`anon key` เปิดเผยได้** ตามการออกแบบของ Supabase เพราะทุก query ที่ใช้กุญแจนี้
> ยังถูก RLS ที่เราเขียนไว้กรองอีกชั้นเสมอ
>
> **`service_role` key ห้ามแตะตอนนี้** — มันข้าม RLS ทั้งหมด Phase 1 ยังไม่มีโค้ดที่ใช้
> ค่อยตั้งตอนทำหน้าจัดการผู้ใช้ใน Phase 2

## ขั้นที่ 6 — ตั้งค่าใน Vercel

Vercel → เลือกโปรเจกต์ → **Settings** → **Environment Variables**

ใส่ 3 ตัวนี้ โดยเลือก scope เป็น **Preview** เท่านั้นในรอบนี้:

| Key                             | Value                      | Scope   |
| ------------------------------- | -------------------------- | ------- |
| `NEXT_PUBLIC_APP_URL`           | URL ของ preview deployment | Preview |
| `NEXT_PUBLIC_SUPABASE_URL`      | Project URL จากขั้นที่ 5   | Preview |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | anon key จากขั้นที่ 5      | Preview |

ตัวแปรที่เหลือใน `.env.example` **ยังไม่ต้องตั้ง** — มีค่า default ในโค้ดอยู่แล้ว
หรือยังไม่มีฟีเจอร์ที่ใช้ (`SENTRY_DSN`, buckets, `SUPABASE_SERVICE_ROLE_KEY`)
ส่วน `APP_COMMIT_SHA` Vercel เติมให้เอง

### เมื่อ Vercel เตือนเรื่อง public prefix

Vercel จะขึ้นข้อความประมาณนี้เมื่อใส่ตัวแปรที่ขึ้นต้นด้วย `NEXT_PUBLIC_`:

> _Remove the public framework prefix to keep this value private._
> _Public prefixes expose values to the browser. If that's safe, change the variable to Config._

**ให้เลือกเปลี่ยนเป็น Config — อย่าลบ prefix**

Vercel เตือนไว้ก่อนเป็นค่าเริ่มต้น เพราะโดยทั่วไปคนมักเผลอใส่ค่าลับด้วย prefix นี้
แต่กรณีของเราคือกรณีที่ค่าเหล่านี้ **ต้องเปิดเผยจริง ๆ**:

| ตัวแปร                          | ทำไมต้องให้เบราว์เซอร์เห็น                                                       |
| ------------------------------- | -------------------------------------------------------------------------------- |
| `NEXT_PUBLIC_APP_URL`           | เป็น URL ของเว็บเอง ซึ่งผู้ใช้เห็นอยู่แล้วในแถบที่อยู่                           |
| `NEXT_PUBLIC_SUPABASE_URL`      | เบราว์เซอร์ต้องรู้ว่าจะยิงคำขอเข้าสู่ระบบไปที่ไหน                                |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase ออกแบบให้เป็น public key ทุก query ที่ใช้กุญแจนี้ยังถูก RLS กรองอีกชั้น |

> ⚠️ **ถ้าลบ prefix ออก เว็บจะพังทันที**
>
> Next.js ฝังค่าลง client bundle เฉพาะตัวแปรที่ขึ้นต้นด้วย `NEXT_PUBLIC_` เท่านั้น
> และแทนค่าด้วยการ match ชื่อแบบข้อความตรง ๆ ตอน build
> ถ้าเปลี่ยนชื่อ เบราว์เซอร์จะได้ `undefined` แล้วหน้าเข้าสู่ระบบจะใช้งานไม่ได้
> (ดู `src/lib/env/client.ts`)
>
> ค่าที่เป็นความลับจริงอย่าง `SUPABASE_SERVICE_ROLE_KEY` **ห้าม**ใส่ prefix นี้เด็ดขาด
> และต้องเก็บเป็น Environment Variable แบบปกติเสมอ

> ⚠️ **ตั้งค่าแล้วต้อง Redeploy** — Deployments → เลือกตัวล่าสุด → เมนู `···` → **Redeploy**
> ค่าใหม่ไม่มีผลกับ deployment ที่ build ไปแล้ว

## ขั้นที่ 7 — สร้างผู้ดูแลระบบคนแรก

ระบบไม่เปิดให้สมัครเอง จึงต้องสร้างบัญชีแรกด้วยมือ

### 7.1 สร้างบัญชี

Dashboard → **Authentication** → **Users** → **Add user** → **Create new user**

- กรอกอีเมล (ใช้ **ตัวพิมพ์เล็กทั้งหมด** — ฐานข้อมูลมี constraint บังคับไว้)
- ตั้งรหัสผ่านชั่วคราวแบบสุ่ม
- ติ๊ก **Auto Confirm User**

คัดลอก **UID** ของผู้ใช้ที่เพิ่งสร้างไว้

### 7.2 ให้สิทธิ์เข้าใช้ระบบ

SQL Editor → แทนค่า 3 จุดในวงเล็บมุม แล้ว Run:

```sql
-- แถวใน profiles คือสิ่งที่ "อนุญาต" ให้บัญชีนี้ใช้ระบบได้
-- บัญชีที่มีใน auth.users แต่ไม่มีแถวที่นี่ จะเข้าสู่ระบบไม่ได้
insert into public.profiles (id, email, title_th, first_name_th, last_name_th, is_active)
values (
  '<UID ที่คัดลอกมา>',
  '<อีเมลตัวพิมพ์เล็ก>',
  'นาย',
  '<ชื่อ>',
  '<นามสกุล>',
  true
);

insert into public.user_roles (user_id, role_code)
values ('<UID ที่คัดลอกมา>', 'SYSTEM_ADMIN');
```

### 7.3 เปลี่ยนรหัสผ่านทันที

ให้เจ้าตัวเข้าระบบแล้วเปลี่ยนรหัสผ่านทันทีในการใช้งานครั้งแรก
และบันทึกไว้ว่าใครเป็นผู้สร้างบัญชีนี้เมื่อใด

## ขั้นที่ 8 — ตรวจว่าใช้งานได้จริง

เปิด Preview URL แล้วไล่ตามนี้

- [ ] เปิด `/login` แล้วเห็นหน้าเข้าสู่ระบบภาษาไทย **ไม่ใช่หน้า error**
- [ ] ไม่มีลิงก์ "สมัครสมาชิก" ที่ไหนเลย
- [ ] กรอกอีเมลผิดรูปแบบ แล้วขึ้นข้อความเตือนภาษาไทย
- [ ] เข้าสู่ระบบด้วยบัญชีผู้ดูแลที่สร้างไว้แล้วเข้าหน้าแรกได้
- [ ] หน้าแรกแสดงชื่อผู้ใช้ วันที่ไทย และรายการสิทธิ์ **25 รายการ**
- [ ] เมนูซ้ายมีหัวข้อ "ผู้ดูแลระบบ" (เพราะเป็น `SYSTEM_ADMIN`)
- [ ] เปิด `/admin/system` ได้ และเห็นค่าตั้งของระบบ
- [ ] เปิด `/api/health` แล้วได้ `{"status":"ok",...}`
- [ ] กด "ออกจากระบบ" แล้วกลับมาหน้า `/login`
- [ ] พิมพ์ `/dashboard` ตรง ๆ ทั้งที่ออกจากระบบแล้ว ต้องถูกเด้งกลับไป `/login`

ถ้าข้อสุดท้ายไม่เป็นไปตามนี้ **อย่าใช้งานต่อ** ให้แจ้งทีมพัฒนาทันที
เพราะแปลว่าการป้องกันสิทธิ์ไม่ทำงาน

## ขั้นที่ 9 — ทำ Production (ตอนใกล้ใช้จริง)

ทำซ้ำขั้นที่ 1–7 โดยเปลี่ยนสามจุด:

1. ตั้งชื่อโครงการเป็น `school-procurement-prod`
2. **ขั้นที่ 3 รันเฉพาะ `seed-reference.sql`** ไม่รัน `seed-sample.sql`
3. ขั้นที่ 6 เลือก scope เป็น **Production** และตั้ง `NEXT_PUBLIC_APP_URL` เป็นโดเมนจริง

เพิ่มเติมก่อนเปิดใช้จริง:

- [ ] เปิด automated backup และกรอก [`backup-restore.md`](backup-restore.md) ให้ครบ
- [ ] **ซ้อมกู้คืนอย่างน้อยหนึ่งครั้ง** ตามเช็กลิสต์ในไฟล์นั้น
- [ ] ตั้ง branch protection บน `main` (แผนข้อ 16.1)
- [ ] ยืนยันว่า Preview ไม่ได้ชี้ไปที่โครงการ prod

## สรุปสิ่งที่ต้องเก็บเป็นความลับ

| ข้อมูล             | ระดับ             | เก็บที่ไหน                                                 |
| ------------------ | ----------------- | ---------------------------------------------------------- |
| `anon key`         | เปิดเผยได้        | ใส่ใน Vercel ได้ตามปกติ                                    |
| Database password  | **ความลับ**       | ที่เก็บรหัสผ่านของโรงเรียน ห้ามลง GitHub                   |
| `service_role` key | **ความลับสูงสุด** | Vercel/Supabase environment เท่านั้น ห้ามลง GitHub เด็ดขาด |
| รหัสผ่านผู้ใช้     | **ความลับ**       | ไม่เก็บที่ไหนเลย ให้ผู้ใช้ตั้งเอง                          |

**ห้าม commit ไฟล์ `.env` หรือ `.env.local` เข้า repository ไม่ว่ากรณีใด** — `.gitignore` กันไว้แล้ว
และ CI มี secret scanning ตรวจซ้ำทุก PR
