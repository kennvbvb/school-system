# 0008 — Budget ledger แบบ append-only และการผูกแหล่งเงินหลายบรรทัด

- **สถานะ:** Proposed — ตารางจะถูกสร้างใน PR-01
- **เกี่ยวข้องกับ:** F-01, F-02, F-16 ใน [`document-audit-findings.md`](../document-audit-findings.md),
  ข้อ 6.1–6.2 ของแผนพัฒนาต่อ, rule codes `BUDGET_INSUFFICIENT` และ `FUNDING_TOTAL_MISMATCH`
- **แทนที่:** ส่วนของ [ADR 0005](0005-money-representation.md) ที่กล่าวถึง `projects.budget_amount`
  ในฐานะยอดคงเหลือ — ADR นี้ทำให้คอลัมน์นั้นกลายเป็นยอดตั้งต้นเท่านั้น

## บริบท

การตรวจเอกสารจริงพบสองอาการที่ schema ปัจจุบันรับไม่ได้

**หนึ่ง — งบติดลบ** โครงการหนึ่งได้งบ 6,000 บาท แต่มีรายการใช้จ่ายรวม 6,199 บาท
สเปรดชีตยอมให้เกิดขึ้นเพราะยอดคงเหลือเป็นผลลัพธ์ของสูตร ไม่ใช่เงื่อนไขที่ต้องผ่านก่อนบันทึก

**สอง — ใช้เงินข้ามโครงการ** มีรายการที่ระบุว่ายืมหรือใช้เงินจากโครงการอื่น
แต่ตารางเก็บโครงการได้ค่าเดียวต่อหนึ่งรายการ ความจริงจึงถูกบันทึกไว้ในช่องคำอธิบาย
ซึ่งรายงานสรุปยอดอ่านไม่ได้

schema ปัจจุบันมี `projects.budget_amount` เป็นคอลัมน์เดียว ถ้าเดินหน้าต่อโดยไม่แก้
ระบบใหม่จะทำซ้ำข้อผิดพลาดเดิมทั้งสองข้อ

## ตัวเลือกที่พิจารณา

### ก. เก็บยอดคงเหลือเป็นคอลัมน์แล้วอัปเดตทุกครั้งที่ใช้จ่าย

ง่ายที่สุดและ query เร็ว แต่ **ยอดคงเหลือกลายเป็นข้อมูลที่แก้ได้โดยไม่มีร่องรอย**
ซึ่งเป็นสาเหตุโดยตรงของ F-01 และ F-09 การกระทบยอดย้อนหลังทำไม่ได้เพราะไม่มีประวัติ
ว่ายอดเปลี่ยนเพราะอะไร

ปฏิเสธ

### ข. คำนวณยอดคงเหลือจากรายการจัดซื้อโดยตรง

ไม่ต้องมีตารางเพิ่ม แต่ **รับการโอนงบและการปรับงบไม่ได้** เพราะการโอนไม่ใช่การจัดซื้อ
และยัง **กันยอดล่วงหน้าไม่ได้** ระหว่างที่รายการรออนุมัติ ทำให้สองรายการที่รออนุมัติพร้อมกัน
ใช้ยอดเดียวกันได้ทั้งคู่

ปฏิเสธ

### ค. Ledger แบบ append-only (เลือกข้อนี้)

ทุกการเปลี่ยนแปลงงบเป็นแถวใหม่ใน `budget_movements` ยอดคงเหลือเป็นผลรวมที่คำนวณจากแถว

## การตัดสินใจ

### บัญชีงบและรายการเคลื่อนไหว

`budget_accounts` คือหน่วยที่ยอดถูกคุมจริง — ผูก `fiscal_year_id`, `project_id`,
`funding_source_id` และ `department_id` (nullable) เข้าด้วยกัน
การคุมยอดที่ระดับนี้แทนระดับโครงการ ทำให้โครงการเดียวที่ได้เงินจากสองแหล่งถูกแยกยอดได้

`budget_movements` เป็น **append-only** ชนิดของ movement ครอบคลุม
`ALLOCATION` / `INCREASE` / `DECREASE` / `TRANSFER_IN` / `TRANSFER_OUT` /
`RESERVE` / `RELEASE` / `COMMIT` / `ACTUAL` / `REVERSAL`

`amount` เป็นจำนวนบวกเสมอ ทิศทางมาจาก `movement_type` ไม่ใช่จากเครื่องหมาย
เพราะจำนวนติดลบทำให้ constraint ตรวจได้ยากและอ่านผิดง่าย

### แก้ผิดด้วย reversal ไม่ใช่ update

การแก้ movement ที่ลงผิดต้องสร้างแถว `REVERSAL` ที่ชี้กลับไปยังแถวเดิม
ห้าม `update` หรือ `delete` แถวเดิม — เหตุผลเดียวกับ audit log:
ยอดที่แก้ได้โดยไม่มีร่องรอยคือยอดที่ตรวจสอบไม่ได้

### การโอนงบต้องเป็นคู่ในทรานแซกชันเดียว

`TRANSFER_OUT` และ `TRANSFER_IN` ต้องเกิดพร้อมกัน ยอดเท่ากัน และชี้หากันด้วย
`paired_movement_id` ผลรวมสุทธิของการโอนหนึ่งครั้งต้องเป็นศูนย์เสมอ
ถ้าครึ่งหนึ่งสำเร็จอีกครึ่งล้ม เงินจะหายหรืองอกจากระบบ

### นิยามยอดที่ใช้ได้

```text
available = ALLOCATION + INCREASE + TRANSFER_IN
          − DECREASE − TRANSFER_OUT
          − RESERVE ที่ยังไม่ถูก RELEASE
          − COMMIT − ACTUAL
          ± REVERSAL ตามแถวที่มันย้อน
```

นิยามนี้ถูกใช้ **ที่เดียว** ใน `src/domain/budget/availability.ts` ทั้ง UI และ server
เรียกฟังก์ชันเดียวกัน เพื่อไม่ให้หน้าจอบอกว่าเงินพอแต่ server ปฏิเสธ

> นิยามนี้ยังเป็น **สมมติฐาน** จนกว่าโรงเรียนจะยืนยันว่าถือ "เงินที่กันไว้แล้วแต่ยังไม่จ่าย"
> เป็นเงินที่ใช้ไม่ได้หรือไม่ (คำถาม Q17 ใน `assumptions.md`)

### ห้ามยอดติดลบ เว้นแต่มีการอนุมัติ

ค่าเริ่มต้นคือปฏิเสธ movement ที่ทำให้ `available` ติดลบ
การยกเว้นต้องเป็น policy ที่เปิดใช้อย่างชัดแจ้ง พร้อมสิทธิ์เฉพาะ เหตุผล และ audit event
— ไม่ใช่ค่าเริ่มต้นของระบบ เพราะค่าเริ่มต้นที่ยอมให้ติดลบคือสิ่งที่ทำให้ F-01 เกิดขึ้นได้

### ปีงบที่ปิดแล้วห้ามสร้าง movement ย้อนหลัง

ยกเว้นบทบาทเฉพาะพร้อม audit — ตรงกับ `requireFiscalYearForDate({ allowClosed })`
ที่มีอยู่แล้วใน `src/domain/master-data/fiscal-year.ts`

### หนึ่งรายการจัดซื้อผูกแหล่งเงินได้หลายบรรทัด

`procurement_funding_allocations` เก็บ `procurement_id`, `budget_account_id`, `amount`
และ `line_no` โดยมี `unique(procurement_id, line_no)`

**ผลรวมของ allocation ต้องเท่ากับ `grand_total` ก่อน submit** และการกันยอดทำต่อ
allocation line ไม่ใช่ต่อรายการ เพื่อให้แต่ละบัญชีงบถูกหักตามส่วนที่มันรับผิดชอบจริง

อาจเก็บ `primary_project_id` ไว้แสดงผลในรายการ แต่ **ห้ามใช้เป็นแหล่งความจริงของยอด**

## ผลกระทบต่อ migration

`projects.budget_amount` ที่มีอยู่แล้วใน migration `20260904000100_master_data.sql`
จะเปลี่ยนความหมายจาก "วงเงินโครงการ" เป็น "วงเงินตั้งต้นที่ใช้สร้าง movement แรก"

แผนการย้ายที่ **ห้ามทำใน PR เดียว**:

1. PR-01 สร้างตารางใหม่ และ backfill หนึ่งแถว `ALLOCATION` ต่อโครงการจากค่าที่มีอยู่
2. PR-01 ยังคงคอลัมน์เดิมไว้และเพิ่มคอมเมนต์ว่าเป็นค่าตั้งต้น ไม่ใช่ยอดคงเหลือ
3. เมื่อ ledger เป็นแหล่งความจริงของทุกหน้าจอแล้ว จึงค่อยพิจารณาถอดคอลัมน์ใน PR ถัดไป

การถอดคอลัมน์พร้อมกับสร้างตารางใหม่จะทำให้ rollback กลับไม่ได้โดยไม่เสียข้อมูล

## ผลที่ตามมา

- query ยอดคงเหลือแพงขึ้นเพราะต้องรวมแถว — แก้ด้วย materialized view หรือ index
  ตามที่วัดผลจริง ไม่ optimize ล่วงหน้า
- ต้องมี integration test ที่ยิง reservation พร้อมกันสองรายการบนบัญชีเดียว
  แล้วยืนยันว่ายอดไม่ติดลบ (ข้อ 8 PR-01 ของแผนพัฒนาต่อ)
- ต้องมี test ที่ยืนยันว่า allocation 6,000 แล้ว reserve 6,199 ถูกปฏิเสธ
  — เป็นการจำลอง F-01 โดยตรง
- audit event ของ movement ต้องเกิดในทรานแซกชันเดียวกับ movement
  ซึ่งปิดหนี้ทางเทคนิคข้อ 2.10 ใน `assumptions.md` ไปด้วย
