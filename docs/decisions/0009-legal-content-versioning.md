# 0009 — ข้อความกฎหมายและแม่แบบเป็นข้อมูลที่มีรุ่นและผู้รับรอง

- **สถานะ:** Proposed — ตารางจะถูกสร้างใน PR-05
- **เกี่ยวข้องกับ:** F-06, F-07, F-19 ใน [`document-audit-findings.md`](../document-audit-findings.md),
  ข้อ 6.5 ของแผนพัฒนาต่อ, rule code `LEGAL_CONTENT_UNPUBLISHED`, AC-04
- **ต่อยอดจาก:** [ADR 0007](0007-immutable-document-snapshots.md)

## บริบท

การตรวจเอกสารจริงพบว่าข้อความอ้างกฎหมายผิดแบบเดียวกัน **ซ้ำกันทั้ง workbook**:
"ข้อ 56" แทน "มาตรา 56" พบใน 10 sheet ของไฟล์หนึ่งและทุก sheet ของอีกไฟล์
รวมถึงการอ้างระเบียบฉบับที่ถูกแทนที่ไปแล้วในเอกสารของปีงบประมาณปัจจุบัน

รูปแบบของความผิดพลาดนี้บอกสาเหตุชัดเจน: **ข้อความถูกคัดลอกต่อกันจากไฟล์เก่า**
เมื่อพิมพ์ผิดครั้งเดียวแล้วคัดลอกต่อ ความผิดจะกระจายไปทุกฉบับและแก้ทีละจุดไม่ไหว

ถ้าระบบใหม่ฝังข้อความกฎหมายไว้ใน JSX หรือไฟล์ค่าคงที่ ปัญหาเดิมจะเกิดซ้ำในรูปแบบใหม่
— แก้ได้ก็ต่อเมื่อ deploy และไม่มีหลักฐานว่าใครรับรองข้อความรุ่นไหน

## ตัวเลือกที่พิจารณา

### ก. เก็บข้อความไว้ในไฟล์ค่าคงที่ในโค้ด

แก้ที่เดียวได้จริง แต่ **ต้อง deploy ทุกครั้งที่กฎหมายเปลี่ยน** และเจ้าหน้าที่พัสดุ
ซึ่งเป็นผู้รู้ว่าข้อความถูกหรือผิด แก้เองไม่ได้ อีกทั้งไม่มีที่บันทึกว่าใครรับรองและเมื่อใด

ปฏิเสธ

### ข. เก็บเป็น master data ธรรมดาที่แก้ได้ทันที

เจ้าหน้าที่แก้เองได้ แต่ **การแก้ข้อความจะเปลี่ยนเอกสารที่ออกไปแล้วด้วย** ซึ่งขัด AC-04
และยังไม่มีขั้นตอนตรวจก่อนใช้ — พิมพ์ผิดแล้วมีผลกับเอกสารฉบับถัดไปทันที

ปฏิเสธ

### ค. ข้อความมีรุ่น มีสถานะ และถูก freeze ลง snapshot (เลือกข้อนี้)

## การตัดสินใจ

### ข้อความกฎหมายเป็นแถวในตาราง ไม่ใช่ string ในโค้ด

`legal_content_versions` เก็บ `code`, `version`, `title`, `body_text`, `source_url`,
`effective_from` / `effective_to`, `status`, `reviewed_by/at`, `approved_by/at` และ `checksum`

`source_url` เป็นฟิลด์บังคับสำหรับข้อความที่อ้างกฎหมาย เพราะการตรวจว่าข้อความถูกหรือผิด
ต้องเทียบกับฉบับราชการได้ — F-06 และ F-07 จะถูกจับได้ตั้งแต่ขั้นตรวจทานถ้ามีลิงก์ต้นทาง

### สถานะบังคับให้มีขั้นตอนตรวจ

`DRAFT` → `PUBLISHED` → `RETIRED`

เฉพาะรุ่น `PUBLISHED` เท่านั้นที่นำไปใช้สร้างเอกสารจริงได้ (`LEGAL_CONTENT_UNPUBLISHED`)
การ publish ต้องมี `approved_by` ที่เป็นบุคคลจริง ไม่ใช่ระบบ

> **ระบบและ AI ไม่รับรองความถูกต้องทางกฎหมาย** ฟิลด์ `approved_by` มีไว้บันทึกว่า
> ผู้มีอำนาจของโรงเรียนเป็นผู้รับรอง ตามแผนข้อ 3.11 และรายงานตรวจข้อ 10

### แม่แบบอ้างรุ่น ไม่ได้ฝังข้อความ

แม่แบบเก็บ `legal_content_version_id` การเปลี่ยนข้อความกฎหมายจึงเป็นการชี้ไปรุ่นใหม่
พร้อมสร้างแม่แบบรุ่นใหม่ ไม่ใช่การแก้ข้อความในที่เดิม

### เอกสารที่ออกแล้วเก็บ "ข้อความ" ไม่ใช่ "ตัวชี้"

ตาม ADR 0007 `issued_documents.snapshot_json` ต้องเก็บ **ตัวข้อความกฎหมายเต็ม ๆ**
ที่ใช้ตอนออกเอกสาร ไม่ใช่แค่ `legal_content_version_id`

เหตุผล: ถ้าเก็บแค่ตัวชี้ การลบหรือแก้แถวในตารางจะทำให้เอกสารเก่าเปลี่ยนหรือ render ไม่ได้
ซึ่งขัด AC-04 การเก็บ `version_id` ควบคู่ไว้ด้วยยังมีประโยชน์สำหรับการค้นหาและรายงาน

### รายชื่อและตำแหน่งผู้ลงนามใช้หลักการเดียวกัน

รายงานตรวจพบว่ารายชื่อคณะกรรมการถูกฝังอยู่ในแบบฟอร์ม
ผู้ลงนามต้องมาจากข้อมูลตำแหน่งที่มีช่วงวันที่มีผล และถูก freeze ลง snapshot ตอนออกเอกสาร
เช่นเดียวกับข้อความกฎหมาย — การเปลี่ยนผู้อำนวยการต้องไม่เปลี่ยนเอกสารเก่า

## ผลกระทบต่อ migration

ไม่มีผลกับ schema ที่มีอยู่ ตารางแม่แบบและเอกสารยังไม่ถูกสร้าง
ADR นี้จึงเป็นการกำหนดรูปร่างก่อนสร้าง ไม่ใช่การเปลี่ยนของเดิม

`document-template-guide.md` ต้องถูกปรับให้อ้าง ADR นี้เมื่อเริ่ม PR-05

## ผลที่ตามมา

- เพิ่มขั้นตอนให้เจ้าหน้าที่: ข้อความใหม่ต้องผ่าน review และ publish ก่อนใช้
  นี่คือ **ต้นทุนที่ตั้งใจรับ** เพื่อแลกกับการไม่ให้ความผิดพลาดกระจายเงียบ ๆ แบบ F-06
- ต้องมี test ที่ยืนยันว่าออกเอกสารด้วยข้อความสถานะ `DRAFT` ไม่ได้
- ต้องมี test ตาม AC-04: ออกเอกสาร → publish ข้อความรุ่นใหม่ → checksum เดิมไม่เปลี่ยน
- ต้องมีหน้าจอให้ผู้มีสิทธิ์ `settings.manage` ดูและเทียบข้อความระหว่างรุ่นได้
  มิฉะนั้นการรับรองจะกลายเป็นการกดปุ่มโดยไม่ได้อ่าน
