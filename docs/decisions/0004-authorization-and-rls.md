# 0004 — Authorization สองชั้น: domain service + RLS

- **สถานะ:** Accepted
- **เกี่ยวข้องกับ:** ข้อ 4.2, 4.3, 13, AC-06, Gate B

## บริบท

แผนบังคับว่า "การตรวจสิทธิ์ต้องทำที่ server/database ไม่พึ่งเพียงการซ่อนปุ่มฝั่ง browser"
และ AC-06 กำหนดว่า "การเรียก endpoint โดยตรงต้องถูกปฏิเสธเช่นเดียวกับ UI"

## การตัดสินใจ

### สามชั้น โดยแต่ละชั้นมีหน้าที่ต่างกัน

| ชั้น           | ที่อยู่               | หน้าที่                             | เชื่อถือได้แค่ไหน                                    |
| -------------- | --------------------- | ----------------------------------- | ---------------------------------------------------- |
| UI             | `visibleSections()`   | ซ่อนเมนูที่ผู้ใช้ใช้ไม่ได้          | **ไม่ใช่การควบคุมการเข้าถึง** เป็นเรื่อง UX เท่านั้น |
| Domain service | `requirePermission()` | ตัดสินใจจริงทุก mutation และทุกหน้า | ชั้นหลัก                                             |
| Database       | RLS policies          | กันกรณีที่โค้ดฝั่งแอปพลาด           | ชั้นสุดท้าย                                          |

**ชั้นที่ 2 คือชั้นที่ตัดสิน** ชั้นที่ 1 และ 3 เป็นส่วนเสริม

### เหตุผลที่ _ไม่_ ตรวจสิทธิ์ใน proxy (middleware)

proxy กันได้เฉพาะ path ที่รู้จักล่วงหน้า และเลี่ยงได้ในบางกรณี
การพึ่ง proxy เป็นชั้นเดียวทำให้ route ใหม่ที่ลืมเพิ่มใน matcher กลายเป็นช่องโหว่เงียบ ๆ
proxy ในระบบนี้จึงทำแค่ต่ออายุ session, ใส่ request ID และส่ง pathname ต่อ

### รายละเอียดของ RLS

- ทุกตารางเปิด RLS และ "ปฏิเสธก่อน" — สิทธิ์ที่ไม่ได้ประกาศคือไม่มีสิทธิ์
- `has_permission(text)` เป็นจุดตัดสินเดียวฝั่งฐานข้อมูล ประกาศเป็น
  `security definer` พร้อม `set search_path = public, pg_temp` เพื่อกัน search_path hijacking
  และ `stable` เพื่อให้ planner ไม่ประเมินซ้ำทุกแถว
- `execute` ถูก revoke จาก `public` แล้ว grant ให้เฉพาะ role `authenticated`
- ตาราง `profiles` **ไม่มี policy สำหรับ `delete`** โดยเจตนา — ปิดบัญชีด้วย `is_active = false`
- ตาราง `permissions` ไม่มี policy สำหรับเขียน เพราะเป็นรายการที่ผูกกับโค้ด แก้ผ่าน migration เท่านั้น

### audit_events เป็น append-only จริง

มีเฉพาะ policy `select` และ `insert` และเพิกถอน `update, delete` ที่ระดับ table privilege ด้วย
การเพิกถอนระดับ privilege สำคัญกว่า เพราะยังมีผลแม้จะมีใครเผลอเพิ่ม policy ผิดในอนาคต

### ลำดับการตรวจใน state machine

`assertTransitionAllowed()` ตรวจ **สถานะก่อนสิทธิ์** โดยเจตนา
เพื่อไม่ให้ผู้ใช้ที่ไม่มีสิทธิ์ใช้ข้อความ error สำรวจว่าระบบมีสิทธิ์อะไรบ้าง
ถ้า action นั้นทำไม่ได้อยู่แล้วในสถานะปัจจุบัน จะได้ `INVALID_TRANSITION` ไม่ใช่ `FORBIDDEN`

## ผลที่ตามมา

- ทุกหน้าใหม่ต้องเรียก `requireUserForPage()` หรือ `requirePermissionForPage()` เอง
  layout ของกลุ่ม `(dashboard)` ตรวจแค่ว่าเข้าสู่ระบบแล้ว ไม่ได้ตรวจสิทธิ์เฉพาะหน้า
- ต้องมี integration test ที่ทดสอบ RLS ด้วย test user หลายบทบาทก่อนจบ Gate B
  → ยังไม่ได้ทำในรอบนี้ เพราะต้องยก Supabase ขึ้นใน CI ก่อน
