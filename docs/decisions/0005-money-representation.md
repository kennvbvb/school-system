# 0005 — การแทนจำนวนเงินด้วยจำนวนเต็มหน่วยสตางค์

- **สถานะ:** Accepted
- **เกี่ยวข้องกับ:** ข้อ 9.1, 9.2, FR-PR-005..007, AC-02

## บริบท

แผนข้อ 9.1 ให้เลือกหนึ่งแนวทางแล้วใช้ทั้งระบบ:

1. เก็บจำนวนเงินเป็น integer หน่วยสตางค์ หรือ
2. ใช้ PostgreSQL `numeric(18,2)` ร่วมกับ decimal library

และห้ามให้ตัวเลขที่แสดงกับตัวเลขใน PDF ใช้ logic คนละชุด

## การตัดสินใจ

**ใช้ทั้งสองอย่าง โดยแบ่งหน้าที่ตามชั้น:**

- **ฐานข้อมูล:** `numeric(18,2)` — เป็นชนิดที่ PostgreSQL รวมยอดและเทียบค่าได้ตรงไปตรงมา
  และอ่านได้ทันทีเมื่อมีคนเปิดดูตารางโดยตรง
- **โดเมนในแอป:** `bigint` หน่วยสตางค์ — คำนวณทุกอย่างด้วย BigInt ไม่แตะ floating point เลย
- **ขอบเขตการแปลง:** `decimalStringToSatang()` และ `satangToDecimalString()` เท่านั้น

### ทำไมต้อง BigInt ไม่ใช่ number

`quantity` เก็บทศนิยม 4 ตำแหน่ง และ `unit_price` ก็ 4 ตำแหน่ง
ผลคูณระหว่างสองค่าที่ scale แล้วโตเกิน `Number.MAX_SAFE_INTEGER` ได้จริงในช่วงค่าที่ระบบรองรับ
BigInt จึงไม่ใช่ทางเลือกด้านความสวยงาม แต่เป็นข้อกำหนดด้านความถูกต้อง

### ทำไมไม่ใช้ decimal library

`decimal.js` หรือ `big.js` แก้ปัญหาเดียวกันได้ แต่เพิ่ม dependency
ในขณะที่ BigInt เป็นของ built-in ที่ให้ผลแม่นยำสัมบูรณ์อยู่แล้ว
สิ่งที่ต้องเขียนเองมีแค่การหารแบบปัดเศษ ซึ่งเป็นฟังก์ชันเดียวและมี test ครบ

### ลำดับการคำนวณและเอกลักษณ์ที่ต้องเป็นจริงเสมอ

```
base (ก่อนส่วนลด ไม่รวมภาษี)
  → discount
    → lineSubtotal (ฐานภาษี)
      → lineTax
        → lineTotal
```

รักษาเอกลักษณ์สองข้อในทุกบรรทัด:

- `lineTotal === lineSubtotal + lineTax`
- `base − discount === lineSubtotal`

ยอดรวมทั้งเอกสารเป็นผลบวกของบรรทัด จึงได้ `grandTotal === subtotal − discountTotal + taxTotal`
โดยไม่มี rounding drift ระหว่างบรรทัดกับยอดรวม

**กรณี INCLUSIVE:** ราคาที่กรอกรวมภาษีแล้ว ระบบถอดภาษีออกเพื่อหาฐานภาษี
แล้ว **คำนวณส่วนลดฝั่งไม่รวมภาษีย้อนกลับ** จาก `base − lineSubtotal`
แทนการปัดเศษส่วนลดแยกอีกครั้ง — ทำให้เอกลักษณ์ข้อที่สองยังเป็นจริงแม้มีการปัดเศษ

### การปัดเศษ

`divideRoundHalfUp()` — ครึ่งขึ้นออกจากศูนย์ เป็นกฎเดียวของทั้งระบบ
เป็นสมมติฐานที่ต้องให้โรงเรียนยืนยัน (ดู `docs/assumptions.md` ข้อ 2.1)

### การปฏิเสธข้อมูลที่ละเอียดเกิน

`parseScaled()` **โยน error** เมื่อได้ทศนิยมเกิน scale ที่กำหนด แทนการปัดให้เงียบ ๆ
เพราะการปัดเงียบ ๆ ทำให้ข้อมูลที่กรอกผิดกลายเป็นยอดที่ดูถูกต้องแต่ไม่ตรงกับเอกสารต้นทาง

## ผลที่ตามมา

- `satangToThaiBahtText()` รับหน่วยสตางค์เท่านั้น และรับจากยอดที่บันทึกไว้แล้ว
  ไม่รับข้อความที่ผู้ใช้พิมพ์เอง (ข้อ 9.2)
