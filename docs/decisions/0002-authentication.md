# 0002 — Authentication ด้วย Supabase Auth และการปิด public sign-up

- **สถานะ:** Accepted
- **เกี่ยวข้องกับ:** FR-AUTH-001..006, ข้อ 14.1

## บริบท

ระบบใช้เฉพาะภายในโรงเรียน ไม่มีผู้ใช้ภายนอก และแผนบังคับว่าต้องปิดการสมัครสมาชิกเอง
โดยผู้ดูแลเป็นผู้เชิญหรือสร้างบัญชี

## การตัดสินใจ

ใช้ Supabase Auth แบบอีเมล+รหัสผ่าน โดยกัน public sign-up **สามชั้น**

1. **ระดับโครงการ** — `enable_signup = false` ใน `supabase/config.toml`
   ทำให้ endpoint สมัครสมาชิกของ Supabase ปฏิเสธตั้งแต่ต้น
2. **ระดับแอปพลิเคชัน** — ไม่มี route, ฟอร์ม หรือลิงก์สำหรับสมัครสมาชิกเลย
   และมี E2E test ยืนยันว่าหน้า `/login` ไม่มีลิงก์ลักษณะนั้น
3. **ระดับข้อมูล** — บัญชีใน `auth.users` ที่ไม่มีแถวคู่กันใน `public.profiles`
   หรือมีแต่ `is_active = false` จะถูก `getCurrentUser()` ปฏิเสธ
   ดังนั้นแม้บัญชีจะถูกสร้างได้ด้วยวิธีใดก็ตาม ก็ยังใช้งานระบบไม่ได้จนกว่าผู้ดูแลจะอนุมัติ

ชั้นที่ 3 สำคัญที่สุด เพราะเป็นชั้นเดียวที่ไม่ขึ้นกับการตั้งค่าที่อาจถูกเปลี่ยนภายหลัง

## รายละเอียดเพิ่มเติม

- ใช้ `supabase.auth.getUser()` ไม่ใช่ `getSession()` ในทุกจุดที่ตัดสินใจเรื่องสิทธิ์
  เพราะ `getUser()` ตรวจ token กับเซิร์ฟเวอร์จริง ส่วน `getSession()` เชื่อ cookie ที่ผู้ใช้ถืออยู่
- ข้อความ error ตอนเข้าสู่ระบบล้มเหลวไม่แยกว่า "ไม่พบอีเมล" หรือ "รหัสผ่านผิด"
  เพื่อไม่ให้ใช้หน้านี้สำรวจว่าอีเมลใดมีบัญชี (ข้อ 19.5) — มี unit test ยืนยัน
- ออกจากระบบใช้ `scope: 'global'` เพื่อให้ตรงกับ FR-AUTH-005 (sign out ทุกอุปกรณ์)
- `returnTo` หลังเข้าสู่ระบบผ่าน `sanitizeInternalPath()` ที่รับเฉพาะ path ขึ้นต้นด้วย `/`
  และปฏิเสธ `//host` ซึ่ง browser ตีความเป็น protocol-relative URL — กัน open redirect

## สิ่งที่ยังไม่ทำ

- **SSO ของโรงเรียน** — FR-AUTH-006 ระบุว่าไม่บังคับใน MVP
  โครงสร้างรองรับได้เพราะ `profiles.id` อ้าง `auth.users.id` ซึ่ง Supabase ใช้ร่วมกันทุก provider
- **Rate limit หน้า login** — ต้องทำก่อน Production (ข้อ 14.1)
  ปัจจุบันพึ่ง rate limit เริ่มต้นของ Supabase Auth เท่านั้น
