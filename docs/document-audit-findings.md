# ข้อค้นพบจากการตรวจเอกสารงานพัสดุของโรงเรียน (ฉบับปกปิดข้อมูล)

> **ที่มา** — สรุปจากรายงานตรวจเอกสารต้นแบบ 6 ฉบับ (ลงวันที่ 4 กันยายน 2569 ผู้ตรวจเชิงระบบ: Codex)
> ไฟล์งานจริงและรายงานฉบับเต็ม **อยู่นอกรีโปนี้และจะไม่ถูกนำเข้ามา** เพราะรีโปเป็น public
>
> **สิ่งที่ถูกตัดออกจากฉบับนี้:** ชื่อโรงเรียน ชื่อบุคคล ชื่อผู้ขาย เลขประจำตัวผู้เสียภาษี ที่อยู่
> เบอร์โทร และชื่อโครงการที่ผูกกับยอดเงินรายโครงการ
>
> **สิ่งที่คงไว้:** ประเภทข้อผิดพลาด จำนวนที่นับได้ ตำแหน่งอ้างอิงระดับ sheet/เซลล์
> และผลต่อการออกแบบระบบ — เพราะเป็นข้อมูลที่ทีมพัฒนาต้องใช้และไม่ระบุตัวบุคคล
>
> ฉบับเต็มที่มีชื่อโครงการและยอดรายรายการ ให้โรงเรียนเก็บไว้นอก GitHub และใช้เป็น
> checklist ปิดงาน P0/P1 ก่อน migration

---

## 1. เหตุใดต้องบันทึกไว้ในรีโป

ข้อค้นพบเหล่านี้ไม่ใช่ความบกพร่องของผู้กรอก แต่เป็นหลักฐานว่า **เครื่องมือเดิม
(สเปรดชีตและเอกสารที่คัดลอกต่อกัน) ไม่มีชั้นที่บังคับความถูกต้องได้**

ระบบใหม่จึงต้องย้ายกฎเหล่านี้ไปอยู่ที่ server และฐานข้อมูล ไม่ใช่ฝากไว้กับวินัยของผู้กรอก
ตารางในข้อ 3 จับคู่ข้อค้นพบกับกลไกที่ต้องมี เพื่อให้ตรวจย้อนได้ว่างานที่ทำครอบคลุม
ปัญหาที่พบจริงหรือยัง

## 2. ข้อสรุปของรายงานตรวจ

ไฟล์ทั้ง 6 ฉบับ **ใช้เป็นแหล่งค้นหาฟิลด์และตัวอย่างหน้าตาได้ แต่ยังใช้เป็นแม่แบบสร้าง
เอกสารอัตโนมัติไม่ได้** สถานะการรับรองจากรายงาน:

| หัวข้อ                               | สถานะ                            |
| ------------------------------------ | -------------------------------- |
| ใช้ไฟล์เป็นแหล่ง requirement         | ผ่านแบบมีเงื่อนไข                |
| ความถูกต้องเชิงสูตร/ข้อมูล           | ไม่ผ่าน จนกว่าจะปิด P0           |
| ความพร้อมพิมพ์จากไฟล์เดิม            | ไม่ผ่าน                          |
| ความพร้อมใช้เป็นแม่แบบ PDF อัตโนมัติ | ไม่ผ่าน จนกว่าจะมี golden sample |
| ความสอดคล้องกฎหมายกลางเบื้องต้น      | มีจุดต้องแก้สำคัญ                |
| ความพร้อมนำข้อมูลจริงเข้า Production | ยังไม่พร้อม                      |

## 4. เกณฑ์กฎหมายกลางที่รายงานใช้เทียบ

บันทึกไว้เป็น **บริบทของการออกแบบ** ไม่ใช่ข้อความที่จะนำไปใส่ในเอกสารจริง
ข้อความที่ใช้จริงต้องมาจาก `legal_content_versions` ที่ผู้มีอำนาจของโรงเรียนรับรอง

- **รายงานขอซื้อ/ขอจ้าง** — ระเบียบกระทรวงการคลังฯ พ.ศ. 2560 ข้อ 22 กำหนดสาระอย่างน้อย 8 กลุ่ม
  (เหตุผลและความจำเป็น, ขอบเขตงาน/คุณลักษณะ, ราคากลาง, วงเงิน, กำหนดเวลา, วิธีและเหตุผล,
  หลักเกณฑ์คัดเลือก, ข้อเสนออื่นเช่นการแต่งตั้งคณะกรรมการ)
  → ระบบต้องเก็บเป็น **ฟิลด์แยก** ไม่ใช่ย่อหน้าเดียว จึงจะตรวจความครบถ้วนได้
- **วิธีเฉพาะเจาะจง** — ฐานอำนาจอยู่ที่ _มาตรา_ 56 แห่งพระราชบัญญัติฯ วิธีดำเนินการอยู่ในระเบียบข้อ 79
- **ระเบียบ พ.ศ. 2535** — ถูกแทนที่แล้วสำหรับหน่วยงานภายใต้กฎหมายปี 2560
- **การตรวจรับและบัญชีวัสดุ** — ระเบียบข้อ 25 (คณะกรรมการ) และข้อ 203–205 (ลงบัญชีแยกชนิด
  มีหลักฐานรับเข้า ตรวจใบเบิกก่อนจ่าย ลงบัญชีทุกครั้ง เก็บหลักฐาน)
  → stock movement ต้องผูกกับเอกสารต้นทางเสมอ และห้ามแก้ยอดย้อนหลังแบบไร้ร่องรอย

> ผู้พัฒนาระบบและ AI **ไม่รับรองความถูกต้องทางกฎหมาย** ข้อความข้างต้นเป็นสิ่งที่รายงานตรวจระบุไว้
> ก่อนใช้งานจริงต้องให้เจ้าหน้าที่พัสดุ หัวหน้าเจ้าหน้าที่ ผู้บริหาร และผู้ตรวจสอบภายใน
> ตรวจรับอีกครั้ง (รายงานตรวจ ข้อ 10)

## 5. สิ่งที่ข้อค้นพบเหล่านี้ **ไม่ได้** บอก

ระบุไว้เพื่อไม่ให้ตีความเกินหลักฐาน และเพื่อกันไม่ให้ระบบ "แก้ให้อัตโนมัติ" โดยเดา

- **ไม่ได้บอกว่าวันที่ที่ถูกต้องคืออะไร** (F-03, F-04, F-10) — ต้องดูจากสัญญา/หลักฐานจริง
- **ไม่ได้บอกว่าลำดับที่ซ้ำควรเป็นเลขใด** (F-12, F-13) — ต้องเทียบกับต้นฉบับที่ถือไว้
- **ไม่ได้บอกว่างบที่ติดลบเกิดจากอะไร** (F-01) — อาจเป็นการโอนงบที่อนุมัติแล้วแต่ไม่ได้บันทึก
  หรือเป็นการใช้เกินจริง ซึ่งมีวิธีแก้ต่างกันโดยสิ้นเชิง
- **ไม่ได้บอกว่ายอดวัสดุที่ถูกต้องคือเท่าใด** (F-09, F-20) — ต้องกระทบยอดกับหลักฐานรับ–จ่าย
- **ไม่ได้ตัดสินว่าช่องว่างทุกช่องคือความผิด** — บางกรณีเป็นข้อยกเว้นที่ถูกต้อง
  จึงต้องมี "สถานะพร้อมเหตุผล" ไม่ใช่บังคับให้กรอกทุกช่อง
- **ไม่ได้จัดประเภทค่าตอบแทนวิทยากรให้** (F-11) — ต้องให้เจ้าหน้าที่การเงิน/พัสดุตัดสิน

ทุกข้อข้างต้นถูกยกไปเป็นคำถาม Q23–Q28 ในหัวข้อ 3 ของ [`assumptions.md`](assumptions.md)

## 6. กติกาการนำข้อมูลเดิมเข้าระบบ

ข้อค้นพบทั้งหมดเกิดกับข้อมูลที่มีอยู่แล้ว การนำเข้าจึงต้อง:

1. เข้า staging table ก่อนเสมอ ห้าม insert ตรงเข้าตารางจริง
2. เก็บ hash ของไฟล์ต้นทาง ชื่อ sheet และเลขแถว เพื่อย้อนกลับไปหาต้นทางได้
3. แยกผลเป็น accepted / warning / rejected และออกรายงานก่อนเขียนจริง (dry-run)
4. รันซ้ำแล้วต้องไม่เกิดข้อมูลซ้ำ (idempotent)
5. **ห้ามแก้ข้อผิดพลาดระดับ P0 ให้อัตโนมัติ** — วันที่ไม่มีจริง เลขซ้ำ และยอดไม่ตรง
   ต้องมีบันทึกการอนุมัติจากผู้รับผิดชอบก่อน
6. ห้าม commit ไฟล์ต้นทางหรือข้อมูลที่สกัดออกมาเข้ารีโป
