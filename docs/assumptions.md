## 2. สมมติไว้ชั่วคราว — ต้องให้โรงเรียนยืนยันก่อนขึ้น Production

แต่ละข้อระบุ **ค่าที่ใช้อยู่**, **เหตุผล**, และ **จุดที่ต้องแก้** หากคำตอบต่างไป

### 2.1 การปัดเศษจำนวนเงิน

- **ค่าที่ใช้อยู่:** ปัดครึ่งขึ้นออกจากศูนย์ (HALF_UP away from zero) ที่ระดับสตางค์
- **เหตุผล:** เป็นแนวปฏิบัติทางบัญชีที่พบบ่อยที่สุดในไทย และแผนบังคับให้ "กำหนดกฎปัดเศษอย่างชัดเจนและมี unit test" (ข้อ 9.1)
- **จุดที่ต้องแก้:** `divideRoundHalfUp()` ใน `src/domain/money/money.ts` เป็นจุดเดียวของทั้งระบบ
- **ผลกระทบถ้าเปลี่ยน:** ต้องรันชุดทดสอบ `tests/unit/calculation.test.ts` ใหม่ทั้งหมด และตรวจกับกรณีตัวอย่างที่โรงเรียนรับรอง (AC-02)

### 2.2 ลำดับการคำนวณและความหมายของ "subtotal"

- **ค่าที่ใช้อยู่:**
  - `subtotal` = ยอดก่อนหักส่วนลด **ไม่รวมภาษี**
  - `grandTotal` = `subtotal − discountTotal + taxTotal`
  - ส่วนลดผูกกับบรรทัด ไม่ใช่ท้ายเอกสาร
- **เหตุผล:** ทำให้เอกลักษณ์ `lineTotal = lineSubtotal + lineTax` เป็นจริงทุกบรรทัด ยอดรวมจึงเท่ากับผลบวกของบรรทัดพอดี ไม่เกิดเศษหลุดระหว่างหน้าจอกับ PDF
- **จุดที่ต้องแก้:** `src/domain/money/calculation.ts`
- **คำถามที่ต้องถาม:** โรงเรียนใช้ส่วนลดท้ายเอกสาร (footer discount) หรือไม่ ถ้าใช้ ต้องนิยามวิธีกระจายส่วนลดลงแต่ละบรรทัดเพิ่ม

### 2.3 ภาษีมูลค่าเพิ่มและภาษีหัก ณ ที่จ่าย

- **ค่าที่ใช้อยู่:** รองรับ `INCLUSIVE` / `EXCLUSIVE` / `EXEMPT` ต่อเอกสาร โดยอัตราภาษีกรอกต่อบรรทัด
- **ยังไม่ได้ทำ:** ภาษีหัก ณ ที่จ่าย (withholding tax) — แผนกล่าวถึงในข้อ 3 แต่ยังไม่มี requirement ID ที่ระบุการคำนวณ
- **คำถามที่ต้องถาม:** ต้องคำนวณและแสดงภาษีหัก ณ ที่จ่ายในเอกสารชุดใดบ้าง และคิดจากฐานใด
- **สถานะ:** **บล็อกการทำ Phase 5 บางเอกสาร** หากคำตอบคือ "ต้องมี"

### 2.4 ข้อความจำนวนเงินภาษาไทย

- **ค่าที่ใช้อยู่:**
  - `0` → `ศูนย์บาทถ้วน`
  - `0.50` → `ศูนย์บาทห้าสิบสตางค์`
  - ค่าติดลบ → เติม `ลบ` นำหน้า
- **จุดที่ต้องยืนยัน:** บางหน่วยงานเขียน `ห้าสิบสตางค์` โดยไม่มี `ศูนย์บาท` นำหน้า
- **จุดที่ต้องแก้:** `satangToThaiBahtText()` ใน `src/domain/money/thai-baht-text.ts`
- **สถานะ:** ไม่บล็อกการพัฒนา แต่ **ต้องยืนยันก่อนพิมพ์เอกสารจริง** (ข้อ 9.2)

### 2.5 เพดานจำนวนเงิน

- **ค่าที่ใช้อยู่:** 999,999,999,999.99 บาท (`MAX_SATANG`)
- **เหตุผล:** สูงกว่างบประมาณโรงเรียนหลายเท่า การมีเพดานช่วยจับข้อมูลที่กรอกผิดหลัก และทำให้ข้อความภาษาไทยไม่ต้องรองรับ "ล้านล้าน"
- **จุดที่ต้องแก้:** `MAX_SATANG` ใน `src/domain/money/money.ts`

### 2.6 ปีงบประมาณ

- **ค่าที่ใช้อยู่:** ฟังก์ชัน `suggestFiscalYearBE()` สมมติว่าปีงบประมาณเริ่ม **1 ตุลาคม**
- **สำคัญ:** ฟังก์ชันนี้ใช้เป็น "ค่าเสนอแนะ" ตอนสร้างรายการเท่านั้น ปีงบประมาณที่มีผลจริงมาจากตาราง `fiscal_years` ซึ่งเก็บ `start_date`/`end_date` จริง
- **คำถามที่ต้องถาม:** โรงเรียนเริ่มและปิดปีงบประมาณวันใด และเริ่มนับเลขเอกสารใหม่เมื่อใด (ข้อ 3)

### 2.7 รูปแบบเลขที่เอกสาร

- **ค่าที่ใช้อยู่:** รูปแบบเป็น pattern ที่แก้ได้ เช่น `{prefix}/{running:4}/{fiscalYearBE}` เก็บใน `document_sequences.format_pattern`
- **ยังไม่ทราบ:** prefix จริงของแต่ละชนิดเอกสาร และ scope ของการนับ (ต่อโรงเรียน / ต่อหน่วยงาน / ต่อชนิดเอกสาร)
- **สถานะ:** โครงสร้างรองรับทั้งสามแบบแล้ว (unique key คือ `document_type + fiscal_year + department`) แต่ **ต้องได้ค่าจริงก่อน Phase 4**

### 2.8 บทบาทและการผูกสิทธิ์เริ่มต้น

- **ค่าที่ใช้อยู่:** 8 บทบาทตามข้อ 4.1 พร้อมชุดสิทธิ์เริ่มต้นใน `DEFAULT_ROLE_PERMISSIONS`
- **สมมติเพิ่มเติมที่ไม่ได้อยู่ในแผน:** `PROCUREMENT_OFFICER` ได้ `procurement.cancel` และ `REQUESTER` ไม่ได้
- **จุดที่ต้องแก้:** ผู้ดูแลระบบปรับผ่านตาราง `role_permissions` ได้โดยไม่ต้อง deploy ใหม่ — ค่าในโค้ดเป็นเพียงค่า seed
- **คำถามที่ต้องถาม:** ใครมีสิทธิ์ยกเลิกรายการที่อนุมัติแล้ว และต้องมีผู้อนุมัติการยกเลิกอีกชั้นหรือไม่ (FR-PR-013)

### 2.9 Separation of duties

- **ค่าที่ใช้อยู่:** **ยังไม่ได้บังคับใช้ในโค้ด** — แผนระบุว่าเป็นกฎที่ "เปิดใช้ได้" (ข้อ 4.2 "หากโรงเรียนเปิดใช้กฎ separation of duties")
- **แผนการทำ:** ทำเป็นค่าตั้งระดับระบบใน Phase 4 พร้อมการตรวจว่าผู้อนุมัติไม่ใช่ผู้ขอ
- **คำถามที่ต้องถาม:** โรงเรียนต้องการเปิดกฎนี้หรือไม่ และมีข้อยกเว้นกรณีใด

### 2.10 การเขียน audit event ในทรานแซกชันเดียวกับข้อมูล

- **ค่าที่ใช้อยู่ใน Phase 1:** `recordAuditEvent()` เขียนแยกจากข้อมูลหลัก
- **เหตุผล:** Phase 1 ยังไม่มี mutation ที่แตะหลายตารางพร้อมกัน จึงยังไม่มีความเสี่ยงเรื่อง atomicity
- **แผนการทำ:** Phase 3 เป็นต้นไป การเปลี่ยนสถานะและการออกเอกสารจะย้ายไปอยู่ใน PostgreSQL function เดียว เพื่อให้ audit event เกิดพร้อมข้อมูลจริงตามข้อ 19.2 ("audit event ถูกสร้างพร้อมธุรกรรม")
- **สถานะ:** **หนี้ทางเทคนิคที่บันทึกไว้แล้ว** ต้องปิดก่อนจบ Phase 4

### 2.11 นิยามของ "ยอดงบที่ใช้ได้"

- **ค่าที่ใช้อยู่:**
  `available = ยอดจัดสรร + เพิ่ม + โอนเข้า − ลด − โอนออก − ยอดที่กันไว้ − ยอดที่ผูกพัน/จ่ายจริง`
- **เหตุผล:** การตรวจเอกสารจริงพบโครงการที่ยอดคงเหลือติดลบ (F-01) ซึ่งเกิดได้เพราะ
  ยอดคงเหลือเป็นผลลัพธ์ของสูตร ไม่ใช่เงื่อนไขที่ต้องผ่านก่อนบันทึก
  การนับ "ยอดที่กันไว้แต่ยังไม่จ่าย" เป็นเงินที่ใช้ไม่ได้ เป็นการตีความที่ปลอดภัยกว่า
- **จุดที่ต้องแก้:** `src/domain/budget/availability.ts` (จะสร้างใน PR-01) เป็นจุดเดียวของทั้งระบบ
- **คำถามที่ต้องถาม:** Q17 — โรงเรียนถือว่าเงินที่กันไว้แล้วแต่ยังไม่เบิกจ่าย เป็นเงินที่ใช้ไม่ได้หรือไม่
- **อ้างอิง:** [ADR 0008](decisions/0008-budget-ledger-and-multi-funding.md)

### 2.12 การห้ามยอดงบติดลบเป็นค่าเริ่มต้น

- **ค่าที่ใช้อยู่:** ปฏิเสธทุกรายการที่ทำให้ยอดใช้ได้ติดลบ การยกเว้นต้องเปิดเป็น policy
  พร้อมสิทธิ์เฉพาะ เหตุผล และ audit
- **เหตุผล:** ค่าเริ่มต้นที่ยอมให้ติดลบคือสิ่งที่ทำให้ F-01 เกิดขึ้นได้ตั้งแต่แรก
- **คำถามที่ต้องถาม:** Q18 — มีกรณีใดที่โรงเรียนต้องบันทึกรายการเกินงบไว้ก่อนแล้วโอนงบตามทีหลัง

### 2.13 ขั้นตอน "ขอใช้เงินโครงการ" เป็น feature ที่ปิดไว้

- **ค่าที่ใช้อยู่:** ยังไม่สร้างตาราง `fund_requests` จนกว่าจะยืนยันว่าใช้ขั้นตอนนี้จริง
- **เหตุผล:** รายงานตรวจพบว่าบันทึกขอใช้เงินโครงการเป็นขั้นตอน **ก่อน** การจัดซื้อจัดจ้าง
  และไม่ได้แทนรายงานขอซื้อ/ขอจ้าง การสร้างตารางโดยยังไม่รู้ว่าใช้จริงหรือไม่
  ทำให้ต้องดูแล schema ที่อาจไม่มีใครใช้
- **คำถามที่ต้องถาม:** Q19

### 2.14 การจัดประเภทรายจ่ายค่าตอบแทนวิทยากร

- **ค่าที่ใช้อยู่:** **ยังไม่ตัดสิน** — ไม่สร้างชุดเอกสารสำหรับรายการประเภทนี้
- **เหตุผล:** รายงานตรวจระบุว่าอาจเป็นค่าตอบแทนการฝึกอบรม ไม่ใช่การจัดซื้อจัดจ้างพัสดุ
  ซึ่งใช้ระเบียบและชุดเอกสารคนละชุด การเดาแล้วออกเอกสารผิดประเภทมีผลทางราชการ
- **คำถามที่ต้องถาม:** Q20 — **บล็อกการทำชุดเอกสารของรายการประเภทนี้**

### 2.15 เวอร์ชันของเครื่องมือ

- **ESLint 9.39.5 ไม่ใช่ 10.x:** `eslint-config-next@16.3.4` ยังพ่วง `eslint-plugin-react` ที่เรียก API เดิมซึ่งถูกถอดออกใน ESLint 10 (ตรวจสอบแล้วว่า lint ล้มจริง) จึงตรึงไว้ที่ 9.x จนกว่า Next.js จะรองรับ
- **TypeScript 5.9.3 ไม่ใช่ 7.x:** `typescript-eslint@8.69.0` ประกาศ peer range `>=4.8.4 <6.1.0` ซึ่งไม่ครอบคลุม TypeScript 7
- **ทบทวนเมื่อ:** มี Next.js รุ่นที่รองรับ ESLint 10 และ typescript-eslint รุ่นที่รองรับ TypeScript 7

## 4. สิ่งที่ **ไม่** ได้ทำโดยเจตนาในรอบนี้

ตามข้อจำกัดในข้อ 25 ของแผน

- **ไม่ทำ PDF template จริง** — แผนห้ามเริ่มก่อนมี golden sample ที่โรงเรียนรับรอง
- **ไม่ฝังชื่อโรงเรียน ผู้บริหาร ข้อความระเบียบ หรือปีงบประมาณ** ลงใน component ใด
- **ยังไม่ทำ inventory, assets และ document templates** — อยู่ใน Phase 4 ถึง 6
- **ไม่เชื่อมต่อ Production หรือใช้ข้อมูลจริง** — seed ทั้งหมดเป็นข้อมูลสมมติที่กำกับคำว่า "(ตัวอย่าง)"
- **ไม่สร้างบัญชีผู้ใช้แรกในโค้ดหรือ seed** — ต้องทำผ่านขั้นตอนที่ควบคุมได้ ดู `docs/deployment.md`
