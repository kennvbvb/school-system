## 2. สมมติไว้ชั่วคราว — ต้องให้โรงเรียนยืนยันก่อนขึ้น Production

แต่ละข้อระบุ **ค่าที่ใช้อยู่**, **เหตุผล**, และ **จุดที่ต้องแก้** หากคำตอบต่างไป

### 2.1 การปัดเศษจำนวนเงิน

- **ค่าที่ใช้อยู่:** ปัดครึ่งขึ้นออกจากศูนย์ (HALF_UP away from zero) ที่ระดับสตางค์
- **เหตุผล:** เป็นแนวปฏิบัติทางบัญชีที่พบบ่อยที่สุดในไทย และแผนบังคับให้ "กำหนดกฎปัดเศษอย่างชัดเจนและมี unit test" (ข้อ 9.1)
- **จุดที่ต้องแก้:** `divideRoundHalfUp()` ใน `src/domain/money/money.ts` เป็นจุดเดียวของทั้งระบบ
- **ผลกระทบถ้าเปลี่ยน:** ต้องรันชุดทดสอบ `tests/unit/calculation.test.ts` ใหม่ทั้งหมด และตรวจกับกรณีตัวอย่างที่โรงเรียนรับรอง (AC-02)

### 2.2 ลำดับการคำนวณและความหมายของ "subtotal"

- **ค่าที่ใช้อยู่:**
  - `subtotal` = ยอดก่อนหักส่วนลด **ไม่รวมภาษี**
  - `grandTotal` = `subtotal − discountTotal + taxTotal`
  - ส่วนลดผูกกับบรรทัด ไม่ใช่ท้ายเอกสาร
- **เหตุผล:** ทำให้เอกลักษณ์ `lineTotal = lineSubtotal + lineTax` เป็นจริงทุกบรรทัด ยอดรวมจึงเท่ากับผลบวกของบรรทัดพอดี ไม่เกิดเศษหลุดระหว่างหน้าจอกับ PDF
- **จุดที่ต้องแก้:** `src/domain/money/calculation.ts`
- **คำถามที่ต้องถาม:** โรงเรียนใช้ส่วนลดท้ายเอกสาร (footer discount) หรือไม่ ถ้าใช้ ต้องนิยามวิธีกระจายส่วนลดลงแต่ละบรรทัดเพิ่ม

### 2.3 ภาษีมูลค่าเพิ่มและภาษีหัก ณ ที่จ่าย

- **ค่าที่ใช้อยู่:** รองรับ `INCLUSIVE` / `EXCLUSIVE` / `EXEMPT` ต่อเอกสาร โดยอัตราภาษีกรอกต่อบรรทัด
- **ยังไม่ได้ทำ:** ภาษีหัก ณ ที่จ่าย (withholding tax) — แผนกล่าวถึงในข้อ 3 แต่ยังไม่มี requirement ID ที่ระบุการคำนวณ
- **คำถามที่ต้องถาม:** ต้องคำนวณและแสดงภาษีหัก ณ ที่จ่ายในเอกสารชุดใดบ้าง และคิดจากฐานใด
- **สถานะ:** **บล็อกการทำ Phase 5 บางเอกสาร** หากคำตอบคือ "ต้องมี"

### 2.4 ข้อความจำนวนเงินภาษาไทย

- **ค่าที่ใช้อยู่:**
  - `0` → `ศูนย์บาทถ้วน`
  - `0.50` → `ศูนย์บาทห้าสิบสตางค์`
  - ค่าติดลบ → เติม `ลบ` นำหน้า
- **จุดที่ต้องยืนยัน:** บางหน่วยงานเขียน `ห้าสิบสตางค์` โดยไม่มี `ศูนย์บาท` นำหน้า
- **จุดที่ต้องแก้:** `satangToThaiBahtText()` ใน `src/domain/money/thai-baht-text.ts`
- **สถานะ:** ไม่บล็อกการพัฒนา แต่ **ต้องยืนยันก่อนพิมพ์เอกสารจริง** (ข้อ 9.2)

### 2.5 เพดานจำนวนเงิน

- **ค่าที่ใช้อยู่:** 999,999,999,999.99 บาท (`MAX_SATANG`)
- **เหตุผล:** สูงกว่างบประมาณโรงเรียนหลายเท่า การมีเพดานช่วยจับข้อมูลที่กรอกผิดหลัก และทำให้ข้อความภาษาไทยไม่ต้องรองรับ "ล้านล้าน"
- **จุดที่ต้องแก้:** `MAX_SATANG` ใน `src/domain/money/money.ts`

### 2.6 ปีงบประมาณ

- **ค่าที่ใช้อยู่:** ฟังก์ชัน `suggestFiscalYearBE()` สมมติว่าปีงบประมาณเริ่ม **1 ตุลาคม**
- **สำคัญ:** ฟังก์ชันนี้ใช้เป็น "ค่าเสนอแนะ" ตอนสร้างรายการเท่านั้น ปีงบประมาณที่มีผลจริงมาจากตาราง `fiscal_years` ซึ่งเก็บ `start_date`/`end_date` จริง
- **คำถามที่ต้องถาม:** โรงเรียนเริ่มและปิดปีงบประมาณวันใด และเริ่มนับเลขเอกสารใหม่เมื่อใด (ข้อ 3)

### 2.7 รูปแบบเลขที่เอกสาร

- **Q3 ได้คำตอบแล้ว — โรงเรียนกำหนดเลขที่เอกสารเอง** ระบบไม่ออกเลขให้อัตโนมัติ
- **ผลต่อการออกแบบ:** ไม่ต้องมีการจอง running number และไม่ต้องมีฟังก์ชัน
  `allocate_document_number` ตามที่แผนเดิมวางไว้ — การสร้างกลไกออกเลขอัตโนมัติ
  ให้กับงานที่ผู้ใช้ตั้งใจพิมพ์เองเป็นความซับซ้อนที่ไม่มีคนใช้ และจะกลายเป็น
  แหล่งความจริงที่สองที่ขัดกับเลขที่โรงเรียนใช้จริง
- **สิ่งที่ยังต้องบังคับ:** ข้อค้นพบ F-12 คือ **เลขซ้ำ** ซึ่งเกิดได้กับการพิมพ์เอง
  เช่นเดียวกับการออกเลขอัตโนมัติ ระบบจึงยังต้องกันเลขซ้ำ
- **ยังไม่ทราบ — ขอบเขตของคำว่า "ซ้ำ"** ใช้ค่าเริ่มต้นว่า **ไม่ซ้ำภายในชนิดเอกสาร
  เดียวกันของปีงบประมาณเดียวกัน** เพราะเป็นขอบเขตที่แคบที่สุดที่ยังจับ F-12 ได้
  โดยไม่บล็อกกรณีที่เอกสารคนละชนิดใช้เลขเดียวกันโดยชอบ
  **ถ้าโรงเรียนนับเลขต่อหน่วยงาน ต้องแก้ก่อนนำเข้าข้อมูลจริง**
- **`formatDocumentNumber()` ยังอยู่** แต่เปลี่ยนบทบาทจาก "ผู้ออกเลข" เป็น
  "ตัวเสนอเลขถัดไป" ที่ผู้ใช้แก้ทับได้ — ดูข้อ 2.17
- **ทำแล้วใน PR-04b** ดูรายละเอียดการตัดสินใจที่ข้อ 2.18 ตาราง `document_numbers`
  ในพจนานุกรมข้อมูล และ migration 0014/0015

### 2.8 บทบาทและการผูกสิทธิ์เริ่มต้น

- **ค่าที่ใช้อยู่:** 8 บทบาทตามข้อ 4.1 พร้อมชุดสิทธิ์เริ่มต้นใน `DEFAULT_ROLE_PERMISSIONS`
- **สมมติเพิ่มเติมที่ไม่ได้อยู่ในแผน:** `PROCUREMENT_OFFICER` ได้ `procurement.cancel` และ `REQUESTER` ไม่ได้
- **จุดที่ต้องแก้:** ผู้ดูแลระบบปรับผ่านตาราง `role_permissions` ได้โดยไม่ต้อง deploy ใหม่ — ค่าในโค้ดเป็นเพียงค่า seed
- **ข้อสังเกตที่พบตอนทำ PR-04a:** ผู้ที่ถือบทบาท `REQUESTER` ล้วน ๆ **ยกเลิกคำขอของ
  ตัวเองไม่ได้** เพราะไม่มีสิทธิ์ `procurement.cancel` เลย ต้องรบกวนเจ้าหน้าที่พัสดุ
  มายกเลิกให้ กฎ separation of duties ไม่ได้ห้ามข้อนี้ — เป็นเรื่องการผูกสิทธิ์เริ่มต้น
  ล้วน ๆ **ไม่แก้ใน PR-04a เพราะเป็นการเปลี่ยนนโยบายสิทธิ์ ไม่ใช่การทำ workflow**
- **คำถามที่ต้องถาม:** ใครมีสิทธิ์ยกเลิกรายการที่อนุมัติแล้ว ต้องมีผู้อนุมัติการยกเลิก
  อีกชั้นหรือไม่ (FR-PR-013) และ **ผู้ขอควรยกเลิกคำขอของตัวเองที่ยังไม่อนุมัติได้หรือไม่**

### 2.9 Separation of duties

- **ค่าที่ใช้อยู่:** บังคับเสมอ ไม่ใช่ค่าตั้งที่ปิดได้ — **ผู้สร้างรายการตรวจสอบหรือ
  อนุมัติรายการของตัวเองไม่ได้**
- **เหตุผลที่ไม่ทำเป็นค่าตั้ง:** ค่าตั้งที่ปิดได้ต้องมีคนตัดสินใจว่าจะเปิดหรือปิด
  และต้องมีหน้าจอให้เปลี่ยน ซึ่งเป็นพื้นที่ผิดพลาดเพิ่มขึ้นเพื่อรองรับทางเลือกที่
  ไม่ควรเลือกตั้งแต่แรก การแยกผู้ขอออกจากผู้อนุมัติเป็นหลักการควบคุมภายในพื้นฐาน
  แนวเดียวกับที่ PR-03 ให้สิทธิ์ยกเว้นผลตรวจเฉพาะ APPROVER ไม่ให้ผู้เตรียมคำขอ
- **โรงเรียนเล็กที่มีคนเดียวทำทั้งสองบทบาท:** ยังทำได้โดยให้บัญชีนั้นถือทั้งสองสิทธิ์
  แต่ต้องสร้างรายการด้วยบัญชีหนึ่งและอนุมัติด้วยอีกบัญชีหนึ่ง — ถ้ากติกานี้ใช้ไม่ได้จริง
  ในทางปฏิบัติ **ต้องแจ้งก่อนใช้งานจริง** เพราะเป็นการเปลี่ยนกติกาควบคุมภายใน
  ไม่ใช่การปรับหน้าจอ

### 2.10 การเขียน audit event ในทรานแซกชันเดียวกับข้อมูล

- **ค่าที่ใช้อยู่ใน Phase 1:** `recordAuditEvent()` เขียนแยกจากข้อมูลหลัก
- **เหตุผล:** Phase 1 ยังไม่มี mutation ที่แตะหลายตารางพร้อมกัน จึงยังไม่มีความเสี่ยงเรื่อง atomicity
- **แผนการทำ:** Phase 3 เป็นต้นไป การเปลี่ยนสถานะและการออกเอกสารจะย้ายไปอยู่ใน PostgreSQL function เดียว เพื่อให้ audit event เกิดพร้อมข้อมูลจริงตามข้อ 19.2 ("audit event ถูกสร้างพร้อมธุรกรรม")
- **สถานะ:** **หนี้ทางเทคนิคที่บันทึกไว้แล้ว** ต้องปิดก่อนจบ Phase 4

### 2.11 นิยามของ "ยอดงบที่ใช้ได้"

- **ค่าที่ใช้อยู่:**
  `available = ยอดจัดสรร + เพิ่ม + โอนเข้า − ลด − โอนออก − ยอดที่กันไว้ − ยอดที่ผูกพัน/จ่ายจริง`
- **เหตุผล:** การตรวจเอกสารจริงพบโครงการที่ยอดคงเหลือติดลบ (F-01) ซึ่งเกิดได้เพราะ
  ยอดคงเหลือเป็นผลลัพธ์ของสูตร ไม่ใช่เงื่อนไขที่ต้องผ่านก่อนบันทึก
  การนับ "ยอดที่กันไว้แต่ยังไม่จ่าย" เป็นเงินที่ใช้ไม่ได้ เป็นการตีความที่ปลอดภัยกว่า
- **จุดที่ต้องแก้:** `src/domain/budget/availability.ts` (จะสร้างใน PR-01) เป็นจุดเดียวของทั้งระบบ
- **คำถามที่ต้องถาม:** Q17 — โรงเรียนถือว่าเงินที่กันไว้แล้วแต่ยังไม่เบิกจ่าย เป็นเงินที่ใช้ไม่ได้หรือไม่
- **อ้างอิง:** [ADR 0008](decisions/0008-budget-ledger-and-multi-funding.md)

### 2.12 การห้ามยอดงบติดลบเป็นค่าเริ่มต้น

- **ค่าที่ใช้อยู่:** ปฏิเสธทุกรายการที่ทำให้ยอดใช้ได้ติดลบ การยกเว้นต้องเปิดเป็น policy
  พร้อมสิทธิ์เฉพาะ เหตุผล และ audit
- **เหตุผล:** ค่าเริ่มต้นที่ยอมให้ติดลบคือสิ่งที่ทำให้ F-01 เกิดขึ้นได้ตั้งแต่แรก
- **คำถามที่ต้องถาม:** Q18 — มีกรณีใดที่โรงเรียนต้องบันทึกรายการเกินงบไว้ก่อนแล้วโอนงบตามทีหลัง

### 2.13 ขั้นตอน "ขอใช้เงินโครงการ" เป็น feature ที่ปิดไว้

- **ค่าที่ใช้อยู่:** ยังไม่สร้างตาราง `fund_requests` จนกว่าจะยืนยันว่าใช้ขั้นตอนนี้จริง
- **เหตุผล:** รายงานตรวจพบว่าบันทึกขอใช้เงินโครงการเป็นขั้นตอน **ก่อน** การจัดซื้อจัดจ้าง
  และไม่ได้แทนรายงานขอซื้อ/ขอจ้าง การสร้างตารางโดยยังไม่รู้ว่าใช้จริงหรือไม่
  ทำให้ต้องดูแล schema ที่อาจไม่มีใครใช้
- **คำถามที่ต้องถาม:** Q19

### 2.14 การจัดประเภทรายจ่ายค่าตอบแทนวิทยากร

### 2.16 เกณฑ์ความคล้ายของชื่อผู้ขาย และสิ่งที่บันทึกลง audit

- **ค่าที่ใช้อยู่:** เตือน (WARN) เมื่อความคล้ายของชื่อหลัง normalize ≥ 0.85
  และบล็อก (BLOCK) เมื่อเลขประจำตัวผู้เสียภาษีและสาขาตรงกัน
- **เหตุผล:** ชื่อผู้ขายภาษาไทยยาวราว 15–30 ตัวอักษรหลัง normalize ค่านี้จึงยอมให้
  ต่างกันได้ราว 2–4 ตัวอักษร ครอบคลุมการพิมพ์ผิดโดยไม่เตือนพร่ำเพรื่อ
  **การบล็อกกรณีชื่อคล้ายจะทำให้บันทึกร้านที่มีอยู่จริงไม่ได้** ซึ่งแย่กว่าการมีข้อมูล
  ซ้ำที่รวมทีหลังได้ ผู้ใช้จึงข้ามคำเตือนได้ด้วยการยืนยัน และระบบบันทึกคำยืนยันไว้
- **ทบทวนเมื่อ:** ใช้งานจริงไประยะหนึ่งแล้วดูว่าเตือนบ่อยเกินไปหรือพลาดของที่ซ้ำจริง

- **audit ของผู้ขายบันทึกเลขประจำตัวผู้เสียภาษี แต่ไม่บันทึกเบอร์โทร ที่อยู่ อีเมล
  และชื่อผู้ติดต่อ:** เลขผู้เสียภาษีเป็นตัวระบุผู้รับเงิน การเปลี่ยนค่านี้คือสิ่งที่
  ผู้ตรวจสอบต้องเห็น ถ้าตัดออก audit trail จะตอบไม่ได้ว่าเงินเปลี่ยนไปเข้าใคร
  ส่วนข้อมูลติดต่อไม่ได้ใช้ตรวจสอบการจัดซื้อ การคัดลอกไปไว้อีกที่จึงเพิ่มความเสี่ยง
  โดยไม่เพิ่มความสามารถในการตรวจสอบ (แผนข้อ 11.2)

- **ข้อจำกัดที่ทราบ:** policy `vendors_select` ให้ผู้ใช้ที่ active ทุกคนอ่านตาราง
  ผู้ขายได้ทั้งแถว รวมเบอร์โทรและที่อยู่ ไม่ได้จำกัดเฉพาะผู้ถือ `masters.read`
  RLS จำกัดได้เป็นรายแถวไม่ใช่รายคอลัมน์ การแยกจึงต้องใช้ view หรือ column privilege
  ซึ่งอยู่นอกขอบเขตรอบนี้ — **ต้องตัดสินก่อนนำข้อมูลผู้ขายจริงเข้าระบบ**

### 2.18 เลขที่เอกสาร — สิ่งที่ตัดสินใจตอนทำ PR-04b

- **การเทียบเลขซ้ำเทียบจากข้อความที่ทำให้เป็นมาตรฐานแล้ว ไม่ใช่จากเลขลำดับ**
  `normalize_document_number()` แปลงเลขไทยเป็นอารบิก ตัดช่องว่าง และลดเป็นตัวพิมพ์เล็ก
  **เหตุผลมาจากไฟล์จริง** ทะเบียนใบสั่งจ้างใช้เลขไทย (`๑๓/๒๕๖๙`) ถ้าเทียบข้อความ
  ตรง ๆ คนที่พิมพ์ `13/2569` จะบันทึกซ้ำได้โดยระบบไม่ทัก ซึ่งเท่ากับไม่ได้ปิด F-12 จริง
- **ไม่ยุบ `/` กับ `-` ให้เป็นตัวเดียวกัน** เอกสารคนละชุดอาจใช้ตัวคั่นต่างกันโดยตั้งใจ
  การยุบจะบล็อกเลขที่ถูกต้อง ซึ่งผู้ใช้แก้ตามไม่ได้ แย่กว่าการมีเลขที่ดูคล้ายกันสองเลข
- **`running_no` เป็นค่าที่ระบบเดา ไม่ใช่ข้อเท็จจริง** กติกาคือ "กลุ่มตัวเลขสุดท้ายที่
  ไม่ใช่ปี" (`ศธ04/0007/2569` ได้ 7 ไม่ใช่ 4) ใช้กับรายงาน F-13 และค่าเสนอแนะเท่านั้น
  **ฐานข้อมูลเป็นผู้แยกเอง ไม่รับจากผู้เรียก** มิฉะนั้นการเรียก RPC ตรงด้วยค่าที่ไม่ตรง
  กับข้อความจะทำให้รายงาน "เลขกระโดดช่วงไหน" โกหก ซึ่งเป็นสิ่งเดียวที่คอลัมน์นี้มีไว้ตอบ
- **ระบบไม่คิดรูปแบบเลขขึ้นเอง** ถ้ายังไม่มีเลขใดในชนิดเอกสารนั้นเลย จะไม่เสนออะไร
  ค่าเสนอแนะคือการต่อจากรูปแบบที่โรงเรียนใช้อยู่แล้วเท่านั้น และผู้ใช้แก้ทับได้เสมอ
- **สถานะสี่ค่าแทนการบังคับให้กรอกเลขทุกแถว** ปิด F-14 (12 แถวในไฟล์จริงไม่มีเลข
  และบางรายการไม่ต้องมีเลขจริง ๆ) การบังคับจะทำให้คนกรอกเลขปลอมเพื่อให้บันทึกผ่าน
  ซึ่งแย่กว่าการบันทึกความจริงว่า "ไม่มีเลข เพราะอะไร"
- **เลขที่ยกเลิกแล้วห้ามนำกลับมาใช้** ทำด้วย unique index ที่ไม่กรอง `VOIDED` ออก
  แถวที่ยกเลิกยังกินที่ในดัชนี จึงไม่ต้องมีตารางเลขต้องห้ามแยกอีกชุด
- **ผู้ที่มีสิทธิ์ `documents.issue` เห็นทะเบียนเลขทั้งเล่ม** ไม่ใช่เฉพาะรายการที่ตัวเอง
  อ่านได้ — การกันเลขซ้ำจะใช้ได้จริงก็ต่อเมื่อคนออกเลขมองเห็นเลขที่ถูกใช้ไปแล้วทั้งหมด
  ตารางนี้ไม่มีข้อมูลส่วนบุคคลของผู้ขายและไม่มียอดเงิน จึงไม่ได้เปิดข้อมูลอ่อนไหวเพิ่ม
- **การบันทึกเลขไม่ผูกกับสถานะของรายการจัดซื้อ** บันทึกข้อความขออนุมัติได้เลขตั้งแต่
  ก่อนอนุมัติ ส่วนใบตรวจรับได้เลขหลังส่งมอบ การบังคับสถานะเดียวจะผิดกับอย่างน้อย
  หนึ่งฉบับ **ถ้าโรงเรียนมีกติกาว่าเอกสารใดออกเลขได้เมื่อใด ต้องแจ้งเพื่อเพิ่มการตรวจ**
- **คำถามที่ยังค้าง:** ขอบเขตความไม่ซ้ำ (ดูข้อ 2.7) และ Q21 — รายการค่าสาธารณูปโภค
  ที่ไม่มีใบสั่งซื้อ ใช้ชุดเอกสารและเลขแบบใด ตอนนี้รองรับด้วยสถานะ `NOT_REQUIRED`
  พร้อมเหตุผล ซึ่งเป็นคำตอบชั่วคราวที่บันทึกความจริงได้ แต่ไม่ได้แทนคำตอบจริง

### 2.19 การกันยอดงบตอนอนุมัติ

- **ปิดช่องโหว่ที่ค้างมาตั้งแต่ PR-03** การตรวจงบตอนส่งอนุมัติเป็นการอ่านยอดแล้วเทียบ
  เท่านั้น สองรายการที่รวมกันเกินงบจึงอนุมัติได้ทั้งคู่จนยอดติดลบ — อาการเดียวกับ F-01
  ชั้นที่บังคับจริงตอนนี้คือการลง `RESERVE` ซึ่งล็อกแถวบัญชีก่อนอ่านยอด
- **กันยอดตอนเข้าสถานะที่ถือยอด คืนตอนออก** ตัดสินจากสถานะก่อนและหลัง ไม่ใช่จาก
  ชื่อ action — เส้นทางใหม่ที่เพิ่มภายหลังจะได้พฤติกรรมที่ถูกต้องโดยอัตโนมัติ
- **ผู้อนุมัติไม่ต้องถือสิทธิ์ `budget.manage`** การบังคับให้ผู้อนุมัติทุกคนถือสิทธิ์จัดการงบ
  เพื่อให้กดอนุมัติได้ คือการขยายสิทธิ์ให้เกินหน้าที่จริง จึงใช้ค่าตั้งระดับทรานแซกชัน
  เป็นเครื่องหมายว่าการลงรายการมาจาก workflow — **อนุญาตเฉพาะ `RESERVE`/`RELEASE`**
- **ใช้วันที่ของวันนี้เป็นวันที่มีผล และไม่ปัดให้เข้าช่วงปีงบ** ถ้าวันนี้อยู่นอกช่วงปีงบของ
  รายการ การอนุมัติจะล้มพร้อมบอกเหตุผล — การปัดวันที่ให้เข้าช่วงคือการบันทึกวันที่ที่
  ไม่ได้เกิดขึ้นจริงลง ledger **ข้อนี้จะกระทบการทำงานช่วงรอยต่อปีงบ ต้องแจ้งโรงเรียน**
- **การอนุมัติเกินงบยังทำได้ถ้ามีสิทธิ์ `budget.override` และระบุเหตุผล** เป็นพฤติกรรม
  เดิมของ `budget_post_movement` ไม่ได้เพิ่มใหม่ — ตรงกับ Q18 ที่ถามว่ามีกรณีใดที่ต้อง
  บันทึกเกินงบไว้ก่อนแล้วโอนงบตามทีหลัง
- **`RECEIVED` ยังถือยอดที่กันไว้** เพราะรับของแล้วแต่ยังไม่ได้เบิกจ่าย เงินยังผูกพันอยู่
  **การแปลงยอดที่กันไว้เป็นค่าใช้จ่ายจริง (`COMMIT`/`ACTUAL`) ยังไม่มีในรอบนี้**
  ยอดที่กันไว้จึงค้างอยู่จนกว่าจะมีขั้นตอนเบิกจ่าย ซึ่งต้องทำก่อนใช้งานจริงเต็มรูปแบบ
- **คำถามที่ยังค้าง:** Q17 (เงินที่กันไว้แล้วแต่ยังไม่เบิกจ่าย ถือเป็นเงินที่ใช้ไม่ได้หรือไม่)
  — ตอนนี้ถือว่า **ใช้ไม่ได้** ซึ่งเป็นค่าเริ่มต้นที่ปลอดภัยกว่า ถ้าโรงเรียนนับต่างออกไป
  ต้องแก้นิยาม `available_amount` ใน view `budget_account_balances`

### 2.20 การจัดการผู้ใช้ — สิ่งที่ตัดสินใจตอนทำ PR-05a

- **ไม่มีปุ่มลบผู้ใช้ มีแต่ปิดบัญชี** โปรไฟล์ถูกอ้างโดยประวัติการอนุมัติ รายการงบ

  การย้ายสิทธิ์ไปบทบาทอื่นจะทำให้กฎเฝ้าของที่ไม่สำคัญแล้วโดยไม่มีอะไรฟ้อง
- **ปิดบัญชีตัวเองไม่ได้เสมอ แม้จะมีผู้ดูแลคนอื่นเหลืออยู่** เป็นกฎที่เข้มกว่าที่จำเป็น
  โดยเจตนา — ความเสียหายของการเผลอกดคือ "เข้ามาแก้เองไม่ได้อีก" ส่วนความไม่สะดวกคือ
  "ต้องให้เพื่อนร่วมงานกดให้" ซึ่งเทียบกันไม่ได้
- **กฎ "ต้องเหลือผู้ดูแลอย่างน้อยหนึ่งคน" ห้ามเฉพาะตอนกำลังจะเสียสิทธิ์**
  ผู้ดูแลคนสุดท้ายยังเพิ่มบทบาทอื่นให้ตัวเองได้ตามปกติ
- **ระบบไม่รับรหัสผ่านเลย** การเพิ่มผู้ใช้ใช้คำเชิญทางอีเมลแล้วให้เจ้าของบัญชีตั้งเอง
  ผู้ดูแลไม่ได้ตั้งและไม่ได้รู้รหัสผ่านของใคร — ปิดช่องที่รหัสผ่านจะไหลผ่าน server action
  แล้วหลุดลง log ซึ่งข้อ 14.2 ห้ามไว้ มี test ที่อ่านไฟล์ schema มาตรวจว่าไม่มีคำว่า
  `password` อยู่จริง เพื่อให้ข้อนี้ไม่ถูกรื้อโดยไม่ตั้งใจ
- **ปุ่มเชิญผู้ใช้ต้องใช้ `SUPABASE_SERVICE_ROLE_KEY`** เพราะ Supabase Auth ไม่ให้
  anon key สร้างบัญชีแทนคนอื่น ถ้ายังไม่ตั้ง ส่วนอื่นของหน้าใช้ได้ปกติ
  และปุ่มเชิญแจ้งเป็นภาษาไทยว่ายังตั้งค่าไม่ครบ แทนที่จะล้มแบบไม่บอกสาเหตุ
- **ผู้ใช้คนแรกยังต้องสร้างจาก Supabase dashboard** หน้านี้แก้ปัญหา "เพิ่มคนที่ 2
  เป็นต้นไปต้องรัน SQL" ไม่ได้แก้การ bootstrap ครั้งแรก ซึ่งเกิดครั้งเดียวตอนติดตั้ง
- **ยังไม่มีการกำหนดสิทธิ์ตามหน่วยงาน** คอลัมน์ `user_roles.department_id` มีอยู่แล้ว
  แต่ยังไม่มี logic ใดใช้ หน้านี้จึงไม่แสดงช่องนั้น เพื่อไม่ให้เข้าใจผิดว่าตั้งแล้วมีผล

### 2.21 การเบิกจ่าย — สิ่งที่ตัดสินใจตอนทำ PR-04d

- **จ่ายได้เมื่อรับของแล้วเท่านั้น** (`PARTIALLY_RECEIVED` หรือ `RECEIVED`)
  การจ่ายก่อนรับของเป็นความเสี่ยงที่ระบบไม่ควรเปิดทางให้โดยปริยาย
  **ยังไม่ครอบคลุมงานจ้างเหมาบริการที่จ่ายตามงวดโดยไม่มีการรับของ — คำถาม Q31**
- **จ่ายเกินยอดที่กันไว้ไม่ได้** ถ้าราคาจริงสูงกว่าที่อนุมัติ ต้องกลับไปขออนุมัติเพิ่มก่อน
  ไม่ใช่ให้ระบบดูดงบส่วนต่างไปเงียบ ๆ ตอนจ่าย
- **ระบบแบ่งยอดข้ามบัญชีงบให้เอง ไม่ให้ผู้ใช้กรอกรายบัญชี** รายการหนึ่งใช้เงินได้
  หลายแหล่ง (F-02) การให้กรอกเองเป็นงานคำนวณด้วยมือที่ผิดได้ง่าย และผิดแล้ว
  ยอดรวมยังตรง จึงไม่มีอะไรฟ้อง
- **เศษสตางค์ไปบรรทัดที่กันไว้มากที่สุด** ไม่ใช่บรรทัดแรก เพราะลำดับที่กรอกไม่มี
  ความหมายทางบัญชี ส่วนบรรทัดใหญ่สุดรับเศษโดยกระทบสัดส่วนน้อยที่สุด
- **สิทธิ์ `procurement.disburse` แยกจาก `budget.manage`** ผู้ที่ตั้งวงเงินเองแล้ว
  จ่ายเงินเองได้คือช่องที่การตรวจสอบภายในต้องมองหา (ข้อ 4.1)
  ค่าเริ่มต้นให้เฉพาะบทบาท `FINANCE` (และ `SYSTEM_ADMIN` ที่ได้ทุกสิทธิ์)
- **ยกเลิกการเบิกจ่ายด้วย `REVERSAL` ไม่ลบแถว** และยกเลิกรายการจัดซื้อที่ยังมี
  การเบิกจ่ายที่ไม่ถูกยกเลิกไม่ได้ ต้องยกเลิกการเบิกจ่ายก่อนเสมอ
- **Q17 ยังค้างอยู่เหมือนเดิม** — PR นี้ทำให้ยอดที่กันไว้ถูกปลดได้แล้ว แต่ไม่ได้
  เปลี่ยนนิยามว่า "กันไว้แล้วยังไม่จ่าย" ถือเป็นเงินที่ใช้ไม่ได้หรือไม่
- **ยังไม่มีชนิด `COMMIT`** ระบบข้ามจาก `RESERVE` ไป `ACTUAL` โดยตรง เพราะยัง
  ไม่มีขั้นตอนก่อหนี้ผูกพันที่แยกจากการจ่ายจริงในกระบวนการของโรงเรียน
  ชนิดนี้มีอยู่ใน enum แล้วและเพิ่มเส้นทางภายหลังได้โดยไม่ต้องแก้ schema

### 2.22 หน้าดูประวัติการใช้งาน — สิ่งที่ตัดสินใจตอนทำ PR-05b

- **ผู้ไม่มีสิทธิ์ `audit.read` มองไม่เห็นแม้แต่แถวของตัวเอง** เป็นข้อที่ตั้งใจ
  ประวัติการตรวจสอบไม่ใช่ข้อมูลส่วนตัวที่เจ้าตัวมีสิทธิ์เรียกดู การเปิดให้ดูของตัวเอง
  ทำให้ผู้ที่ทำผิดรู้ว่าตัวเองถูกบันทึกอะไรไว้
- **ไม่แสดง `ip_hash` และ `user_agent`** ทั้งคู่มีไว้สืบสวนเป็นรายกรณี ไม่ใช่ข้อมูล
  ที่ควรไหลผ่านหน้าที่เปิดดูทุกวัน (ข้อ 14.2)
- **ไม่มีการส่งออกเป็นไฟล์ในรอบนี้** การส่งออกประวัติทั้งระบบเป็นการเคลื่อนย้าย
  ข้อมูลส่วนบุคคลออกนอกระบบ ซึ่งต้องตอบ Q11 (เก็บนานเท่าใด ใครมีสิทธิ์ export) ก่อน
- **ไม่แสดงจำนวนทั้งหมดและไม่มีเลขหน้า** ตารางโตตลอดเวลา การนับทั้งตารางทุกครั้ง
  ที่เปิดหน้าเป็นงานหนักที่ให้ตัวเลขซึ่งล้าสมัยทันทีที่แสดงผล
- **ค่าตัวกรองที่ผิดรูปแบบถูกปัดทิ้ง ไม่ทำให้หน้าล้ม** ผู้ตรวจสอบที่แก้ URL เอง
  แล้วเจอหน้า error จะไม่รู้ว่าต้องแก้อะไร
- **การเปรียบเทียบ before/after ดูเฉพาะคีย์ระดับบนสุด** ค่าซ้อนแสดงเป็น JSON ย่อ
  การไล่ลงลึกทำให้รายการยาวจนอ่านไม่ออก ซึ่งแย่กว่าการเห็น JSON ก้อนเดียว

### 2.23 รายงานงบประมาณ — สิ่งที่ตัดสินใจตอนทำ PR-09a

- **สิทธิ์ที่ใช้คือ `budget.read` ไม่ใช่ `reports.export`** หน้านี้เป็นการดูบนจอ
  ไม่ใช่การนำข้อมูลออกนอกระบบ ผู้ที่เห็นยอดรายบัญชีอยู่แล้วจึงควรเห็นยอดรวมได้ด้วย
  — ถ้าใช้ `reports.export` ผู้อนุมัติที่ต้องดูยอดคงเหลือก่อนอนุมัติจะเข้าไม่ได้
- **ค่าเริ่มต้นนับบัญชีที่ปิดแล้วด้วย** บัญชีที่ปิดแล้วยังถือยอดที่ใช้ไปของปีนั้น
  การซ่อนไว้เป็นค่าเริ่มต้นจะทำให้ยอดรวมน้อยกว่าความจริงโดยที่หน้าจอดูปกติทุกอย่าง
- **บัญชีที่ไม่ได้ผูกกับมิติที่เลือกมีกลุ่มของตัวเอง** ไม่ถูกซ่อน บัญชีงบผูกครบ
  ทั้งสาม scope ไม่ได้เสมอไป การซ่อนเท่ากับทำให้เงินก้อนนั้นหายจากรายงาน
- **ยอดที่กันไว้ถูกนับเป็นเงินที่ใช้ไม่ได้แล้ว** ในสัดส่วนการใช้งบ เป็นสมมติฐาน
  เดียวกับ `availability.ts` ซึ่งยังรอคำตอบ **Q17**
- **ไม่มีการส่งออกเป็นไฟล์ในรอบนี้** กติกา export ของ PR-09 (typed date ใน XLSX,
  print area, export log, การปิดบังข้อมูลตามบทบาท) ต้องทำให้ครบพร้อมกัน
  การปล่อยปุ่มดาวน์โหลดก่อนจะได้ไฟล์ที่เปิดกับ Excel ภาษาไทยแล้วอ่านยอดผิด
- **ยังไม่มีรายงานทะเบียนจัดซื้อจัดจ้างและรายงานสถานะเอกสาร** ซึ่งอยู่ในขอบเขต
  PR-09 เช่นกัน แยกออกไปเป็นคนละ PR ตามกติกาหนึ่ง PR ต่อหนึ่งเรื่อง

### 2.24 การผูกพันงบ — สิ่งที่ตัดสินใจตอนทำ PR-04e

- **`ISSUED` คือจุดที่เกิดข้อผูกพัน** ไม่ใช่ `APPROVED` เพราะการอนุมัติเป็นเรื่อง
  ภายในโรงเรียน ส่วนใบสั่งซื้อคือสิ่งที่ส่งออกไปหาผู้ขายแล้ว
- **`RECEIVED` ยังผูกพันอยู่** รับของแล้วแต่ยังไม่จ่าย เงินยังต้องกันไว้ให้
  ถ้าปล่อยคืนตอนรับของ เงินที่ยังต้องจ่ายผู้ขายจะกลับไปอยู่ในงบที่ใช้ได้
- **ยอดผูกพันยังรวมอยู่ในช่อง "ใช้ไปแล้ว" เหมือนเดิม** ยังไม่แยกเป็นช่องที่ห้า
  ในหน้าบัญชีงบและรายงาน — ข้อมูลอยู่ใน ledger ครบแล้ว การแยกช่องเป็นการอ่าน
  อย่างเดียวที่ทำต่อได้โดยไม่แตะเส้นทางเงิน และควรทำพร้อมคำตอบของ **Q32**
  ซึ่งจะบอกว่าโรงเรียนต้องการเห็นยอดผูกพันแยกในรูปแบบใด
- **ลำดับการแปลงยอดคือคืนก่อนแล้วจึงผูกพัน** สลับลำดับแล้วบัญชีที่งบตึงจะถูก
  ปฏิเสธว่างบไม่พอ ทั้งที่ยอดสุทธิไม่เปลี่ยน
- **`ACTUAL` คืนด้วย `RELEASE` ไม่ได้** เงินที่จ่ายออกไปแล้วต้องย้อนด้วย `REVERSAL`
  ซึ่งทิ้งร่องรอยว่ามีการจ่ายผิดเกิดขึ้นจริงให้ผู้ตรวจสอบเห็น

### 2.25 ทะเบียนจัดซื้อจัดจ้าง — สิ่งที่ตัดสินใจตอนทำ PR-09b

- **สิทธิ์ที่ใช้คือ `procurement.read.all` ไม่ใช่ `reports.export`** เหตุผลเดียวกับ
  ข้อ 2.23 (หน้านี้เป็นการดูบนจอ) บวกอีกข้อหนึ่ง: "ทะเบียน" ที่เห็นเฉพาะรายการ
  ของตัวเองคือสมุดคุมที่ไม่ครบเล่ม ผู้อ่านจะสรุปยอดของโรงเรียนจากมันโดยไม่รู้ว่า
  ยังขาดอะไรอยู่ จึงไม่เปิดให้ผู้ที่มีเพียง `procurement.read.own`
- **ค่าเริ่มต้นแสดงทุกสถานะ** รวมฉบับร่าง รายการที่ไม่อนุมัติ และที่ยกเลิกแล้ว
  ด้วยเหตุผลเดียวกับข้อ 2.23 — การซ่อนเป็นค่าเริ่มต้นทำให้ยอดรวมน้อยกว่าความจริง
  หน้าจอจึงบอกไว้ชัดว่ายอดรวมนี้ไม่ใช่ยอดที่โรงเรียนใช้จ่ายจริง
- **กรองด้วย "วันที่ขอ" ไม่ใช่วันที่ออกใบสั่งซื้อ** เพราะเป็นช่องเดียวที่ทุกแถว
  มีเสมอ การกรองด้วยวันที่ออกใบสั่งซื้อจะทำให้รายการที่ยังไม่ออกใบสั่งซื้อหายไป
  ทั้งหมด ทั้งที่เป็นรายการที่ต้องติดตามที่สุด — โรงเรียนอาจต้องการวันที่อื่น
  ซึ่งเป็นคำถาม **Q34**
- **ตรวจความครบถ้วนเฉพาะรายการที่ออกใบสั่งซื้อไปแล้ว** (`ISSUED` เป็นต้นไป)
  ถ้าตั้งข้อสังเกตตั้งแต่ฉบับร่าง ทุกแถวจะติดธงจนธงไม่เหลือความหมาย
  และข้อสังเกตเป็นเพียงการยกขึ้นมาบอก ไม่ใช่การตัดสินว่าผิดระเบียบ (ข้อ 12 ของแผน)
- **เลขที่เอกสารที่ถูกยกเลิกยังแสดงอยู่** ถ้าตัดทิ้ง รายการที่เคยมีเลขแล้วถูกยกเลิก
  จะดูเหมือนรายการที่ไม่เคยมีใครแตะเลย ทั้งที่สองอย่างนี้ต้องติดตามคนละแบบ
- **ไม่แบ่งหน้า แต่มีเพดาน 1,000 แถว และเมื่อเกินเพดานจะไม่แสดงยอดรวมเลย**
  การแบ่งหน้าแล้วคิดยอดรวมจาก query อีกชุดจะทำให้ตัวเลขสองส่วนค่อย ๆ ไม่ตรงกัน
  ส่วนยอดรวมของข้อมูลที่ไม่ครบซึ่งติดป้ายว่า "ยอดรวม" คือคำตอบที่ผิดและน่าเชื่อ
- **ผู้ขายที่ถูกลบแบบ soft delete จะไม่มีชื่อแสดง** สำหรับผู้ที่ไม่มี `masters.manage`
  ตาม RLS ของ `vendors` — แถวของทะเบียนยังอยู่ครบ หายเฉพาะชื่อ
- **ยังไม่มีการตรวจเลขซ้ำและเลขกระโดด (F-12, F-13)** ซึ่งเป็นเรื่องของทะเบียน
  เลขที่เอกสาร ไม่ใช่ของทะเบียนรายการ จึงอยู่ในรายงานสถานะเอกสารที่ยังไม่ได้ทำ
- **ไม่มีการส่งออกเป็นไฟล์ในรอบนี้** ด้วยเหตุผลเดียวกับข้อ 2.23

### 2.26 รายงานสถานะเอกสาร — สิ่งที่ตัดสินใจตอนทำ PR-09c

- **ทั้งรายงานตั้งอยู่บนค่าที่ระบบเดา** `running_no` แยกจากข้อความของเลขที่เอกสาร
  ด้วยการเดา (ดู `extractRunningNumber()`) ไม่ใช่ค่าที่โรงเรียนกรอกเข้ามา
  หน้าจอจึงมีคำเตือนอยู่เหนือตัวเลขทุกตัว และ **ไม่มีปุ่มแก้เลขอัตโนมัติ**
  ตามกลไกที่ระบุไว้สำหรับ F-13 คือ "ห้ามแก้อัตโนมัติโดยเดา"
- **ขอบเขตของลำดับคือ (ปีงบ × ชนิดเอกสาร)** ซึ่งตรงกับ `document_numbers_unique_idx`
  ที่กันเลขซ้ำอยู่จริง ถ้ารายงานใช้ขอบเขตอื่น มันจะรายงานช่องว่างของลำดับที่
  ระบบไม่ได้คุมอยู่ — **ถ้าโรงเรียนนับเลขต่อหน่วยงาน ต้องแก้ทั้ง index และรายงานนี้**
- **เลขที่ "ถูกใช้ไปแล้ว" คือ `ISSUED` และ `VOIDED`** เลขที่ยกเลิกแล้วห้ามนำกลับมาใช้
  จึงไม่ใช่ช่องว่าง ถ้านับเป็นช่องว่าง รายงานจะชวนให้คนไปกรอกเลขที่ระบบจะปฏิเสธ
- **การวิเคราะห์ลำดับนับเลขของรายการที่ถูกลบด้วย แต่รายการข้อยกเว้นไม่นับ**
  ตั้งใจให้ต่างกัน: เลขของรายการที่ถูกลบยังกินที่ในดัชนี การกรองออกจะประกาศ
  ช่องว่างปลอมที่ไม่มีทางเติมได้ ส่วนรายการข้อยกเว้นเป็นงานที่ต้องตามต่อ
  และไม่มีใครต้องตามเอกสารของรายการที่ถูกลบไปแล้ว

### 2.30 ปิด direct insert ของ audit_events — สิ่งที่ตัดสินใจตอนทำ PR-S01

ที่มา: รายงานตรวจสอบ 27 กันยายน 2569 ทิ้งงานนี้ไว้ตอนแก้ PR #20 (ข้อ 2.28)
เพราะกระทบ RLS ของตารางที่ทุก mutation ในระบบใช้ร่วมกัน จึงแยกมาทำบน `main`
โดยตรงในชื่อ PR-S01 ไม่ผูกกับ PR สายแผนใด (ไม่มีเลข PR-0x)

- **ช่องโหว่จริง**: policy `audit_events_insert` เดิมตรวจแค่
  `current_profile_is_active()` ไม่ได้ตรวจว่า `actor_id` ที่ผู้เรียกส่งมาตรงกับ
  ผู้เรียกจริงหรือไม่ ผู้ใช้ที่มี valid session (เช่น เปิด dev tools แล้วเรียก
  Supabase REST API ตรง ข้าม Next.js server action ทั้งหมด) จึง `insert` แถวที่
  `actor_id` เป็นคนอื่นได้ — audit_events เป็นตารางเดียวที่ระบบอ้างว่า
  "append-only แก้ไม่ได้ ตรวจสอบย้อนหลังได้เสมอ" แต่ตัวตนผู้กระทำกลับปลอมได้

  `budget_movements`/`stock_movements`) แล้วสร้าง RPC `record_audit_event()`

  `auth.uid()` ของผู้เรียกเองเสมอ **ไม่มีพารามิเตอร์ให้ระบุ actor เองเลย** จึง

  ซึ่งไม่ถูก grant/revoke ของ `authenticated`/`anon` บังคับอยู่แล้ว — เหตุผล
  เดียวกับที่ตารางเหล่านั้นเองก็ไม่มี insert policy ให้ผู้ใช้ทั่วไป
- **ลบพารามิเตอร์ `actorId` ออกจาก `AuditEventInput`** (`src/server/audit/audit-log.ts`)
  ผู้เรียกทุกจุด (9 ไฟล์) ไม่ต้องส่งมาอีกต่อไป เพราะ RPC เป็นผู้กำหนดเองแล้ว —
  ตรวจแล้วว่าทุกจุดเดิมส่ง `actorId` เป็นผู้ใช้ปัจจุบันของ session นั้นเองอยู่แล้ว
  (ไม่มีจุดใดตั้งใจบันทึกแทนคนอื่น) การลบพารามิเตอร์จึงไม่เปลี่ยนพฤติกรรมที่ถูกต้อง
  อยู่แล้ว มีแต่ปิดช่องที่ทำผิดได้จากภายนอกแอป
- **ยังไม่รองรับเหตุการณ์ก่อนมี session** เช่น `auth.login_failed` (พิมพ์รหัสผ่าน

  โค้ด (มีแค่ชนิดที่ประกาศไว้ใน `AuditAction`) จึงยังไม่ต้องแก้ในรอบนี้ ถ้าจะทำ

**ผู้เบิกกับผู้อนุมัติต้องเป็นคนละคน** (หลักการแยกหน้าที่ — สมมติเป็นค่าเริ่มต้น ผ่อนได้ถ้าโรงเรียนมีขั้นตอนอื่น) เรียก RPC ตรงก็เลี่ยงไม่ได้
**ขอบเขตที่ยังไม่ทำ:** การอนุมัติ "ในระบบ" (ใบเบิก pending → ผู้อนุมัติกดอนุมัติด้วยบัญชีตน → จึงลง ledger) ตอนนี้ระบบยังเป็นการบันทึกว่าใครอนุมัติ
(จากเอกสารกระดาษ) แล้วฐานข้อมูลตรวจว่าผู้นั้นมีอำนาจจริง ยังพิสูจน์ไม่ได้ว่าผู้อนุมัติ "ยินยอม" จริง ต้องรู้ขั้นตอนจริงของโรงเรียนก่อนจึงออกแบบได้

**ยังไม่ได้รันบน PostgreSQL จริงในสภาพแวดล้อมที่พัฒนา PR นี้** เหตุผลเดียวกับ
ข้อ 2.29 (ไม่มี Docker/Supabase CLI ในสภาพแวดล้อมนี้) — migration และ SQL test
ผ่านการอ่านทวนมืออย่างละเอียดเทียบกับ `budget_ledger_rls.sql`/`audit_read_test.sql`
ที่ผ่านการทดสอบจริงมาแล้ว ถ้า CI พบปัญหาจะแก้ทันทีในรอบติดตาม PR นี้

## 4. สิ่งที่ **ไม่** ได้ทำโดยเจตนาในรอบนี้

ตามข้อจำกัดในข้อ 25 ของแผน

- **ไม่ทำ PDF template จริง** — แผนห้ามเริ่มก่อนมี golden sample ที่โรงเรียนรับรอง
- **ไม่ฝังชื่อโรงเรียน ผู้บริหาร ข้อความระเบียบ หรือปีงบประมาณ** ลงใน component ใด
- **inventory เริ่มแล้วบางส่วนใน PR-07** (บัตรบัญชีพัสดุ + ledger + stock card
  พื้นฐาน — ดูข้อ 2.29) แต่ยังไม่มีการเชื่อมกับใบตรวจรับจริง, การแบ่ง lot/batch,
  หรือการอัปโหลดไฟล์หลักฐานการปรับยอด — assets และ document templates ยังไม่ทำ
  อยู่ใน Phase 5 ถึง 6
- **ไม่เชื่อมต่อ Production หรือใช้ข้อมูลจริง** — seed ทั้งหมดเป็นข้อมูลสมมติที่กำกับคำว่า "(ตัวอย่าง)"
- **ไม่สร้างบัญชีผู้ใช้แรกในโค้ดหรือ seed** — ต้องทำผ่านขั้นตอนที่ควบคุมได้ ดู `docs/deployment.md`
